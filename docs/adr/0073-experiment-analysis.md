# 0073. 実験の結果から、期待する科目をどの段で落としたかと、誤って選んだ科目を数える

- ステータス: 承認
- 日付: 2026-10-30

## 文脈

- 推薦の精度は、評価(`experiment run`、ADR 0048)、比べ(`experiment pair` と `compare`、ADR 0053、0055)、確かめ用での確かめ(ADR 0067)の道具で回している。何を直すかを決める分析だけは、その都度 scratchpad に使い捨てのスクリプトを書いていた
- その分析で、LLM のスキルで候補に入らなかった期待する科目 25 件のうち 17 件は、評価データの手書きのスキルなら 20 位以内に入ると分かり、読み取りが一番の弱点だと決めた(ADR 0065 の前の調べ)。この数はリポジトリから作り直せない
- 次はモデルの入れ替え(読み取りと選び直し)を比べる。替えるたびに、どの段で良くなり、どの段で悪くなったかを同じ物差しで見たい
- 結果の JSON には試行ごとに、読み取った解釈とスキル、候補、選んだ授業とその判定、期待する科目が候補にあったか、選んだか、中心につながらず外したかが残っている。期待する科目が候補に入らなかったとき、それが読み取りのせいか検索のせいかは残っていない

## 検討した選択肢

読み取りと検索の切り分け

1. 分析のときに、評価データの手書きのスキルで同じ取り方の検索をし直し、それなら候補に入る科目を「読み取りで落とした」と数える
2. 保存した結果だけで分ける。候補に入らなかったかまでで、読み取りと検索は分けない
3. 実験のときに、手書きのスキルの候補も結果の JSON に書く

コマンドの置き場

1. `experiment analyze`(run、pair、compare と並べる)
2. 別の CLI

## 決定

高橋さんが、切り分けは 1、置き場は 1 を選んだ。

- `experiment analyze <結果の JSON>` は、採点した推薦(compare と同じに、全職業がそろった回だけ。そろった回が無ければ全ての回)の期待する科目を、次の 6 つの行方に分けて数える
  - 中心に選んだ
  - 土台に選んだ
  - 土台に選んだが中心につながらず外した
  - 候補にあったが選ばなかった(選び直しで落とした)
  - 候補に無く、手書きのスキルなら候補に入る(読み取りで落とした)
  - 候補に無く、手書きのスキルでも入らない(検索で落とした)
- 選んだ授業(中心、土台、外した土台)ごとに、判定(期待、土台、少数、関係なし)の内訳を出す
- 落とした回数の多い期待する科目と、関係なしで選んだ回数の多い科目を、それぞれ上から 10 件出す
- 読み取りで落とした数の多い職業を上から 5 件、その推薦で読み取った解釈とスキル、評価データの手書きのスキルと並べて出す
- 手書きのスキルの検索は、今の DB と設定で行う。結果の評価データの指紋(`config.dataset`)が `--dataset` のファイルと違うときと、埋め込みのモデル、検索の取り方、候補の数が今の設定と違うときは断る
- 確かめ用の評価データ(ADR 0067)は、職業と科目ごとの結果を出すことになるので断る
- 失敗した推薦は数えない

## 理由

- 一番の弱点を数で示せ、モデルを替えたときに、読み取りと検索のどちらが動いたかが分かる。前に流した結果も分析できる
- 3 は実験の形が変わり、前の結果を分けられない
- 流す、分析する、比べるが 1 つのコマンドに並び、評価から改善までの手順として説明しやすい

## 受け入れたトレードオフ

- 手書きのスキルの検索に DB と埋め込みが要る(50 職業で検索文 300 ほど、0.1 円未満)
- 取り込み直しや埋め込み直しのあとに前の結果を分析すると、結果のときの検索とずれうる。DB の中身は結果に残っていないので、確かめられない(ADR 0048 と同じ)
- 手書きのスキルで入るかどうかで読み取りのせいと決めるので、手書きのスキルそのものが弱い職業では、読み取りの取りこぼしを検索のせいと数える
- `experiment.py` がさらに長くなる

## 再検討する条件

- 手書きのスキルを見直して、読み取りで落とした数の物差しが変わるとき
- 2 つの結果の行方の差を並べたくなったとき(今は compare の指標と、それぞれの analyze を見比べる)
