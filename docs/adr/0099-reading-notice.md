# 0099. 職業名を広く読み替えたことを作成中の画面で知らせ、完成の画面のその場で別の職業名で作り直せるようにする

- ステータス: 承認
- 日付: 2026-11-08

## 文脈

- 職業の読み取りは、学科の授業に無い応用分野や道具で決まる細かい職種(Webエンジニアなど)を、授業で備えられる広い職業として読み、そう読んだことを前提の 1 文に書く(ADR 0032)。前提の無い解釈は入力した職業名のままにする(ADR 0037)
- 今は、完成の画面にだけ、入力した職業名(解釈と違うとき)と前提の 1 文を出している。作成中の画面は入力した職業名のまま 10〜30 秒進み、読み替えたことは完成してから分かる
- 解釈に納得しない利用者は、入力の画面に戻り、回生、始める学期、クラスの選択、先に入れる授業(ADR 0093)を入れ直して作り直すしかない
- 読み替えは珍しくない。50 職業の pair の読み取り 300 回のうち 48 回が「ITエンジニア」だった(ADR 0065)

## 検討した選択肢

知らせ方

1. 作成中と完成の画面で知らせ、完成の画面に作り直す導線を置く。API の呼び出しは増えない
2. 作る前に読み取りだけ行い(約 0.1 円)、解釈を確かめてから作る。誤った道標を作らないが、全ての利用者に 1 手順増え、API が 2 段になる
3. 今のまま(完成の画面に前提を出すだけ)

作り直す導線

1. 結果の画面のその場で職業名を入れ直して作る。回生、始める学期、学科、クラスの選択、先に入れる授業は、この道標と同じ条件のまま
2. 入力の画面へ、条件を URL で渡して初期値にして移る。条件も替えられるが、入力の画面が URL から初期値を読み、クラスの選択と先に入れる授業の一覧の読み込みと突き合わせる作りが要る
3. 入力の画面へ移るだけ。条件を入れ直す手間が残る

作成中の画面への読み取りの渡し方

1. worker が段を書くときに、読み取った職業も道標に書き、`GET /api/v1/plans/{id}` が返す。作成中の画面は今の段の読み直しのまま受け取れる
2. 読み取りだけを返す API を別に足す。画面の読み直しが 2 本になる

## 決定

高橋さんが、知らせ方は 1 を(2026-11-05)、作り直す導線は 1 を(2026-11-08)選んだ。渡し方は 1 にする。

- 推薦は、読み取りのあとの段(検索、選び直し)に入ると知らせるときに、読み取った職業(入力した職業名、解釈、前提、スキル)も渡す。worker は段と一緒にその職業を道標に入れ、道標の決まり(作成中だけ、職業名が条件と同じ)で確かめてから書く。配置の段に入るときも推薦の職業を書くので、残した推薦に当たって検索と選び直しを飛ばしたとき(ADR 0092)も書く
- 道標は作成中のあいだだけ読み取りを持つ(段と同じ。完了すれば結果の職業になり、失敗すれば消す)。plans に `reading`(JSONB。結果の JSON の職業と同じ形。作成中でなければ空。マイグレーション 0013)を足す
- `GET /api/v1/plans/{id}` と道標を返す API は `reading`(結果の `profile` と同じ形)を返す。待ちのあいだと読み取りの前、完了と失敗のあとは null
- 作成中の画面は、読み取りに前提があれば「〈解釈〉として作っています」と前提の 1 文を出す(入力した職業名と解釈が同じでも、前提があれば出す)。今の段を読み上げる枠の中に置き、出たときに読み上げる。行先表示は入力した職業名のままにし、完成で行先が替わるのを巻き取りの動き(ADR 0084)で見せる
- 完成の画面は、前提があるとき、前提の下に「別の職業名で作り直す」を置く。押すと職業名の欄(空)と、条件は同じまま職業名だけ替えると断る一言、「作り直す」と「やめる」が開き、職業名の欄にフォーカスを移す。送ると、この道標の条件のまま職業名だけ替えて `POST /api/plans` し、新しい道標へ移る。入力した職業名と同じ名前(前後の空白を除く)は送らずにその場で断る。断られたら(1 日の上限、作成中の道標、選べなくなったクラスなど)API の文をその場に出す。条件で断られたとき(422。クラスの選択や先に入れる授業を、あとで「もう取った」と答えたときなど)は、その場では条件を替えられないので、入力の画面への導線も出す。やめるで閉じ、押したボタンにフォーカスを返す。開き直すと職業名の欄は空に戻る
- 前提の無い道標には導線を置かない。作り直す前の道標は残す

## 理由

- 作成中に知らせると、待つあいだに解釈が分かり、完成を待たずに納得できるかを考えられる。解釈を先に確かめる案は誤った道標を作らないが、読み替えない多くの利用者にも 1 手順と待ちを足す
- 段と一緒に書けば、作成中の画面がすでに行っている道標の読み直しで受け取れ、API も画面のポーリングも増えない。段を書くのに失敗しても作成を続ける今の決まり(段を書けなくてもログに残して続ける)に、読み取りもそのまま乗る
- その場で作り直すのは、読み替えに納得しない利用者が直したいのは職業名だけで、ほかの条件は同じだから。入力の画面へ引き継ぐ案は条件も替えられるが、作りが大きい
- 同じ職業名を断るのは、推薦を残しているので(ADR 0092)同じ道標になり、1 日の上限だけを使うため

## 受け入れたトレードオフ

- 作り直しも 1 日 3 件の上限(ADR 0038)に数える。読み替えに納得しなかった分も数える
- その場の作り直しでは条件を替えられない。替えたいときは入力の画面から作る
- 作り直す前の道標は残る。要らなければ利用者が消す
- 作成中の道標の行に読み取りの分が増える(数百バイト)

## 再検討する条件

- 前提のある道標の作り直しが多いとき(読み取りの指示文を見直す)
- 作成中に知らせても、完成の画面で作り直す利用者が多いとき(解釈を先に確かめる案)
