# 0031. 画面は道標を路線に見立てた見た目にし、時間割帳と行き来でき、作成中は worker が書く段を見せる

- ステータス: 承認
- 日付: 2026-10-19

## 文脈

フェーズ 8 で 3 つの画面ができた(ADR 0030)。見た目は Tailwind の既定の色と文字で、どの Web サービスにもありそうな姿になっている。高橋さんは、画面をもっと作り込みたいと考えている。

結果の画面の方向性として、次の 3 つを見本で比べた。

- 路線図: 卒業までを路線に見立て、学期を駅として縦に並べる
- ダッシュボード: 暗い地にカードとグラフを並べる
- 時間割帳: 週の時間割を主役にし、学期をタブで切り替える

作成中の画面は今、待ちか作成中かしか分からない。worker は道標を作る間に、職業の解釈、検索、選び直し、配置の 4 つの段を順に進む(ADR 0029)。0029 は、進み具合を画面に見せたくなったときを再検討の条件にしている。

画面に出す「中心 / 土台」の呼び名は、選び直しの区分(ADR 0023)をそのまま訳したもので、画面の言葉としては硬い。LLM への指示文は区分を core と foundation と書いているので、理由の文に「(core)」のような英語が混ざることがある。

## 検討した選択肢

見た目の方向性

1. 路線図(道しるべ)
2. ダッシュボード
3. 時間割帳

路線と時間割帳の行き来

1. 両方。画面全体を「路線 / 時間割帳」で切り替え、路線の駅ごとにも時間割を開け、駅から時間割帳のその学期へ移れる
2. 画面全体の切り替えだけ
3. 駅ごとに開くだけ

区分の呼び名

1. 柱 / 礎(いしずえ)
2. 要(かなめ)/ 布石
3. 峰 / 麓
4. KEY / STEP

作成中の進み具合

1. worker が段ごとに道標の行に書き、GET が返す
2. 画面が経過時間から段を進める
3. 段は出さず経過時間だけを出す

明るい見た目と暗い見た目

1. 明るい見た目を既定にし、画面の隅の「ダークモード」のボタンで切り替える
2. 端末の設定に合わせる

ログイン前の紹介

1. 本物の出力から作った見本の道標を見せる
2. 説明と図だけ

## 決定

高橋さんが、方向性は 1、行き来は 1、呼び名は 1、進み具合は 1、ログイン前の紹介は 1 を選び、明るい見た目を既定にして隅に「ダークモード」のボタンを置くと決めた。作成中の段の言葉と、現れる動きを足すことも決めた。

見た目

- 卒業までを路線に見立てる。紙の地図のような生成りの地に、見出しは明朝(Shippori Mincho)、本文はゴシック(Zen Kaku Gothic New)。色は案内標識の朱と藍で、柱の授業は朱、礎の授業と路線は藍
- 文字は next/font で取り込み、ビルドのときにアプリに入れる(利用者のブラウザから外のフォントの配信元へは取りに行かない)
- 部品は Tailwind だけで書く(ADR 0030)。色は全て CSS の変数にし、明るい見た目と暗い見た目の両方を定める
- 明るい見た目が既定。画面の隅の「ダークモード」のボタンで切り替え、選んだ見た目はブラウザ(localStorage)に覚える。読み込みの直後に見た目が切り替わってちらつかないよう、描く前に小さなスクリプトで当てる
- 現れる動き(駅が順に現れる、作成中の段が脈打つ)を足す。動きを減らす設定(prefers-reduced-motion)の利用者には出さない

結果の画面

- 道のり: 路線の見た目で、学期を駅として縦の線に並べ、駅ごとに授業のカード(柱か礎か、理由、コマ、クラス、単位)を出す。駅ごとに「この学期の時間割を開く」でその場に週の時間割を開き、「時間割帳で見る」で時間割帳のその学期へ移る。最後は卒業の駅で、通る単位と授業の数を出す
- 時間割帳: 学期をタブで切り替え、週の時間割に授業を付箋のように置き、横に理由のメモを並べる
- 上に「道のり / 時間割帳」の切り替えを置く。見え方の名前は、路線、道標、地図、行程と比べて高橋さんが「道のり」を選んだ(道標は結果そのものの呼び名なので見え方には使わない)。見え方と学期は URL のクエリに持ち、共有と戻るができる

呼び名

- 中心は「柱」、土台は「礎」と書く。礎の授業は「確率統計の礎」のように、前提にする柱の授業と合わせて書く
- API とデータの区分の値(core / foundation)は変えない。呼び名は画面の言葉だけ
- 選び直しの指示文で、理由の文には core、foundation、prerequisite_for などの英語の語を書かず、授業の名前で書くよう求める。指示文を変えたので選び直しの評価を測り直す
- 測り直し(gpt-5.4-nano で 1 回、10 職業): 中心の適合率 56%、期待する科目を中心に選んだ割合 88%、選んだ科目のうち関係なし 18%(ADR 0023 は 3 回で 58%、83%、15%)。理由 127 件のうち英語の区分の語を含むものは 0 件

作成中の進み具合

- 道標に今の段(stage)を持たせる。値は analyzing(職業の解釈)、searching(検索)、selecting(選び直し)、placing(配置)で、作成中のときだけ持ち、終わったら空にする
- worker は道標を取るときに analyzing を書き、そのあと段に入るたびに道標の行に段を書く。推薦のユースケースは自分の手順(検索、選び直し)に入るたびに知らせる関数を受け取り、BuildPlans がそれを道標の段に直して書く。段の書き込みは見せるためだけのものなので、失敗しても ERROR のログに出して道標の作成は続ける
- GET の道標は段を返す。移行の前に取られた道標は作成中でも段が空のことがあり、画面は最初の段として見せる。画面は 4 つの段を次の言葉で順に出し、今の段を脈打たせる: 「目的地を地図に書き込んでいます」→「道を探しています」→「通る授業を選んでいます」→「道標を立てています」。待ちの間は「順番を待っています」

ログイン前の紹介

- ログインしていないときのトップは、何ができるかと、3 つの手順(職業を入れる → 授業を選ぶ → 卒業までの時間割に並べる)、本物の出力から作った見本の道標(路線の見た目で一部)を見せてから、ログインへ誘う
- 見本は本物の API の応答の形で frontend に置き、どの年度の時間割から作ったかを書く。API も OpenAI も呼ばない

PR の分け方

- 1 つ目: ADR、段の記録と API、選び直しの指示文と測り直し
- 2 つ目: 画面の作り直し

## 理由

- 路線図は、shirube(道標)という名前と画面の見た目が一致し、卒業までの流れが一目で分かる。週の時間割は時間割帳で補える
- 時間割帳は、履修登録の下書きにそのまま使え、時間割の重なりや空きが一番分かりやすい。駅から開けば流れを見ながら週も確かめられ、時間割帳では学期をまたいで見比べられる
- 「柱 / 礎」は明朝の見出しと合い、礎の上に柱が立つという関係が言葉のまま伝わる
- worker が書けば本当の進み具合を出せ、まだ最初の段なのに「並べています」と出すような嘘がない
- 明るい見た目は路線図の紙の地図の雰囲気に合う。暗い見た目は使いたい人だけが選べばよい
- 見本の道標を見せれば、ログインする前に何ができるかが分かる

## 受け入れたトレードオフ

- Web フォントの分だけ読み込みが重くなる
- 明るい見た目と暗い見た目の両方の色を保つ手間が増える
- 段を書くたびに DB への書き込みが 1 件あたり 3 回増える(analyzing は道標を取る書き込みに含める)。推薦のユースケースに段を知らせる口が増える
- 移行が 1 つ要る
- 見本の道標は、時間割を入れ替えると古くなる(年度を書いて示す)
- 指示文を変えたので、選び直しの評価を測り直す費用(約 15 円)がかかる

## 再検討する条件

- 見本の道標が今の時間割と大きく食い違ったとき(作り直す)
- 段の書き込みが DB の負荷として目立ったとき
- 時間割帳の方がよく使われると分かったとき(既定の見え方を変える)
