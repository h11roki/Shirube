# 0055. 比べる 2 つの設定を同じ時間に交互に流し、差ありを職業ごとの並べ替え検定で判定する

- ステータス: 承認
- 日付: 2026-10-23

## 文脈

ADR 0053 で、2 つの実験の結果を職業ごとに対応をとったブートストラップの 95% 信頼区間で比べ、区間が 0 を含まなければ差ありとした。誤りの率は 10 職業で確かめ、同じ設定どうしの組は主に同じ実験の回どうし(21 組)で、続けて流した実験どうしは 1 組だけだった。

評価データを 30 職業にして(ADR 0054)、ADR 0053 の再検討する条件のとおり誤りの率を確かめ直した(README の「30 職業での比べ」)。

- 30 職業の同じ実験の回どうし(1 回と 1 回、6 組、39 の比べ)で、ブートストラップの差ありは 4(10%)、職業ごとに前と後を入れ替える並べ替え検定の p < 0.05 は 2(5%)。ブートストラップは、差が一部の職業にしか出ない指標(検索の再現率で 30 職業のうち 9 職業)で、差の無い職業を何度も選び直すので区間が狭く出る
- 別の時刻に流した同じ設定の 2 組(初めの 10 職業、3 回と 3 回)は、どちらも後の方が関係なしが 9 ポイントほど低く(23.2% → 13.9%、16.0% → 7.3%)、並べ替え検定でも差ありになった。推薦のコード、モデル、指示文、正解は同じで、多くの職業で同じ向きに下がった

職業を選び直す区間も並べ替え検定も、職業ごとの差が互いに独立で、同じ設定なら前と後を入れ替えてよいことを前提にする。流した時刻で多くの職業が同じ向きにずれると、その前提が崩れ、ずれが設定の効果に見える。今までの比べは設定ごとに別の時刻に流していた(10 職業の改善の記録は 10:40 から 13:34、30 職業の基準と今の既定は続けて 16:51 と 17:03)。

## 検討した選択肢

比べ方

1. 比べる 2 つの設定を 1 つのプロセスで、職業と回の組ごとに交互に流し、差ありを職業ごとの並べ替え検定で判定する。区間はブートストラップで出し続ける
2. 作りは変えず、判定だけ並べ替え検定にし、比べる 2 つを続けて流す決まりにする。軽いが、時刻の揺れは残る
3. 比べのたびに基準をもう 1 回流し、同じ設定どうしの差より大きいかで見る。作りは小さいが、費用が 1.5 倍(30 職業で 1 回約 100 円)

2 つの設定の指定

1. `experiment pair --label <名前> --before 設定=値 … --after 設定=値 …`。どちらも今の環境の設定から始め、違う設定だけ書く。今と同じ形の JSON を 2 つ書くので、compare も今までの結果もそのまま使える
2. `run --versus 設定=値 …` で、今の設定と書き換えた設定を交互に流す。コマンドは増えないが、run の結果が 1 つのときと 2 つのときがある

組の中の順番

1. 職業と回の組ごとに、前と後のどちらを先に流すかを交互に入れ替える
2. いつも前を先に流す。読み取りの指示文のように両方で同じ入力があると、後に送った側だけが入力のキャッシュで安くなる

交互に流していない 2 つの結果の比べ

1. 「別の時間に流したので、差に時刻の揺れが入る」と断って、判定も区間も出す。今までの結果どうしも比べられる
2. 差ありの判定は交互に流した組だけに出す。誤った差ありを読ませないが、今までの記録の判定を出し直せない

作ったあとの確かめ

1. 今の既定どうしを 30 職業 × 3 回で交互に流す(約 130 円)
2. 流さない

## 決定

高橋さんが、比べ方は 1、指定は 1、順番は 1、交互でない比べは 1、確かめは 1 を選んだ。

- `python -m app.presentation.cli.experiment pair --label <名前> --before 設定=値 … --after 設定=値 …` を足す。設定は環境変数と同じ名前で書き、替えられるのは推薦の道の設定(`CHAT_MODEL`、`SELECTION_MODEL`、`SELECTION_CANDIDATE_LIMIT`、`SELECTION_VOTES`、`SELECTION_VOTE_DELAY_SECONDS`、`OCCUPATION_READING_CACHE_SIZE`)だけにする。DB や埋め込みのモデル、年度は前と後で同じでないと比べられない。前と後が同じ設定でもよい(同じ設定どうしの確かめに使う)
- 2 つの設定で推薦の道をそれぞれ組み立て(読み取りを覚える場所も別)、評価データの職業と回の組ごとに前と後を 1 件ずつ流す。組の番号(回 × 職業の並びで 0 から)が偶数なら前を先に、奇数なら後を先に流す
- `--repeat`、`--profiles`、`--dataset`、`--judgments`、`--out` は run と同じ。費用の上限 `--budget` は 2 つの合計に掛け、既定は run の 2 倍の 200 円。止め方(料金表に無いモデル、3 回続けての失敗、Ctrl-C、SIGTERM、SIGHUP、DB の失敗)は run と同じで、止めたらそこまでに流した推薦を両方に残す
- 結果は run と同じ形の JSON を 2 つ(`<日時>-<名前>-before.json` と `<日時>-<名前>-after.json`)に書き、どちらにも組の名前、前か後か、相手のファイル名を残す
- `experiment compare` は、差ありを職業ごとの並べ替え検定で判定する。両方にそろった職業ごとに前と後を丸ごと入れ替える組み合わせを 10,000 通り(乱数の種 0)作り、差の絶対値が実際の差以上になる割合を両側の p 値とし、p < 0.05 なら差あり。p 値も出す。ブートストラップの 95% 区間は差の大きさと悪い側の端を読むために出し続ける。採点した回の数が前と後で違うとき、入れ替えると割合を出せない組があるとき、そろった職業が 10 に満たないときは判定を出さない
- 同じ pair の前と後でない 2 つを比べるときは、「別の時間に流したので、差に時刻の揺れが入る」と出す
- 判定は、変える前に ADR に書いたねらいの指標で行う(ADR 0053 のまま)
- 指示文やコードの違いは設定で切り替えられないので、今までどおり続けて流し、断りの付いた比べとして読む
- 作ったあと、今の既定どうしを交互に 30 職業 × 3 回流し、差ありが出ないかと、関係なしの差が別の時刻に流したときの 9 ポイントより小さいかを確かめる

## 理由

- 交互に流すと、流した時刻によるずれが前と後に同じようにかかり、差から消える
- 並べ替え検定は、30 職業の回どうしで誤りが名目の 5% に近く、差が一部の職業にしか出ない指標でも、区間のように狭くならない
- 区間は、差の大きさと、ねらいでない指標がどこまで悪くなりうるかを読むのに要る
- pair は今と同じ形の JSON を書くので、compare も今までの結果も変えずに使える
- 組ごとに先を入れ替えると、両方で同じ入力を送ったときに入力のキャッシュで安くなる得が、前と後に半分ずつになる

## 受け入れたトレードオフ

- 判定の方法(並べ替え検定)と大きさの目安(ブートストラップの区間)が別になる。区間が 0 を含まないのに p ≥ 0.05、またはその逆のときは、検定の判定に従う
- 並べ替え検定は区間より見つける力が弱くなりうる(10 職業の 25 の比べでは差ありが 3 と 6)
- 設定で切り替えられない違い(指示文、コード)は交互に流せない
- 交互に流しても、1 つのプロセスの中で前と後が API の上限を分け合う。1 件ずつ順に流すので、時間は 2 つを続けて流すのと変わらない
- 確かめに約 130 円かかる

## 再検討する条件

- 交互に流した同じ設定どうしで、差ありが 5% を大きく超えるとき
- 指示文の案を何度も比べるようになったとき(指示文を設定で切り替えられるようにして交互に流す)
- 評価データの職業を増やしたとき
