# 0017. 検索の評価の正解は、検索の候補の全科目を 3 体が職業名だけから独立に判定した多数決で作る

- ステータス: 承認(資料作りと集計は 0054 でスクリプトにした)
- 日付: 2026-10-15

## 文脈

ADR 0016 で、検索を職業 10 件の評価データで測り、科目名単位の再現率@10 と @20 を出すと決めた。その正解(期待する科目)は Claude が科目名から当てて下書きしたもので、シラバスを読み直すと理由が中身とずれた科目があり、名前から中身の分かりにくい実験や演習の科目は 1 つも入っていなかった。

最初の作り直しでは、学科の専門・基礎専の 82 科目だけを 3 体の LLM に判定させた。レビューで次の 2 点が分かった。

- 検索は教養を含む 188 科目名から選ぶ。判定されていない教養科目(データサイエンス・AI基礎など)は正解になれないのに上位を争い、期待する科目を押し下げる
- 判定者に検索文と同じ手書きのスキルを渡したので、正解が検索文の言葉に引っ張られる。フェーズ 5 で検索文を LLM のスキルに替えると、正解が手書きのスキル寄りのままになり、公平に比べられない

フェーズ 5 ではアプリの LLM がシラバスを読んで科目を選ぶ方向で考えているので、正解を作る判定はアプリとは別の系統の LLM か人が行う必要がある。

## 検討した選択肢

判定の範囲

1. 検索の候補の全科目(2026 年度の情は 188 科目名)
2. 専門・基礎専の 82 科目だけにし、検索の候補も同じ範囲に絞る
3. 82 科目のまま、ずれを受け入れる

判定者に渡す職業の情報

1. 職業名だけ
2. 職業名と、検索文と同じ手書きのスキル

判定の担い手

1. 立場の違う 3 体の LLM が独立に判定し、多数決で決める。割れたものだけ高橋さんが決める
2. Claude 1 体が判定し、高橋さんが全てを確かめる
3. 高橋さんが全てを判定する

## 決定

範囲は選択肢 1、職業の情報は選択肢 1、担い手は選択肢 1。ADR 0016 の検索文と指標の決定は、下の「評価」にそのまま書き写してこの ADR で引き継ぐ。0016 は正解の作り方を覆されたので廃止にし、評価の決定はこの ADR だけを読めば分かるようにする。

評価

- 評価データ(`backend/eval/occupations.json`)は、年度、学科と、職業 10 件を持つ。職業ごとに名前、必要なスキル(検索文に使う)、期待する科目(時間割表の科目名と理由)を書く
- 検索文は職業名と手書きのスキルをつなげたもの。フェーズ 5 で LLM のスキルに差し替えて比べる
- 検索の候補は、その学科の 1〜4 回生に今年度開講されている科目(`CourseSection.offered_to`)。時間割表の入学年度の範囲は今年度その授業を取る学年の入学年度を表すので、回生 G に開講されているとは、今年度 G 回生にあたる入学年度(年度 − G + 1)が範囲に入り、G が履修できる回生に含まれること
- 科目のスコアは、その科目名の全クラスのシラバスのチャンクのうち最も近いものの類似度。指標は期待する科目の再現率@10 と @20 を職業ごとと平均で出す
- 候補が無いとき、その年度が今のモデルで埋め込み終わっていないときは、検索は止める

正解の作り方

- 判定する科目は、検索の候補の全科目。区分(専門、基礎専、教養など)で絞らない
- 判定者は 3 体の LLM(Claude Code のサブエージェント、Claude Opus 5.5)で、立場を分ける: 採用・育成担当のエンジニア、カリキュラムを設計する教員、進路を考える 3 回生。科目が多いので、科目を 2 つに分けて同じ立場の 2 体に渡し、立場ごとに結果を合わせる
- 判定者に渡すのは、科目ごとのシラバスの抜粋(授業の概要と方法、到達目標、授業スケジュールのテーマ)と、職業名だけ。手書きのスキル、既存の評価データ、他の判定者の結果は見せない。指示文は `backend/eval/judge-prompt.md`
- 判定者は職業ごとに各科目を「中心(授業の中心テーマがその職業の仕事で直接使う知識・技能そのもの)」「土台(基礎、または一部の回で触れる)」「関係なし」に分け、中心と土台には根拠を付ける。根拠はシラバスの中身を自分の言葉で 40 字以内に要約したもので、原文を写さない
- 2 体以上が中心とした科目を期待する科目にする。1 体だけが中心とした科目は高橋さんが中心か土台かを決める
- 全ての判定(関係なし以外の票と根拠、シラバスの主コード)、判定者に渡した科目の分け方、高橋さんの決定を `backend/eval/judgments.json` に残す。期待する科目の理由には、中心とした判定者の根拠を使う(まとめ方は `backend/eval/judge-prompt.md`)

## 理由

- 判定の範囲を検索の候補とそろえると、検索が正しく上位に出した科目を正解として数えられ、判定していない科目に押し下げられることが無い
- 判定者に検索文の言葉を渡さないので、正解が特定の検索文に有利にならず、フェーズ 5 で検索文を替えても同じ正解で公平に比べられる
- 立場を分けた独立の判定と多数決で 1 体の偏りを薄め、人が見るのは割れた箇所だけになる
- 根拠と票を残すので、正解を後から確かめ、学科や年度を増やすときに同じ手順で判定し直せる

## 受け入れたトレードオフ

- 3 体は同じ系統の LLM なので、立場を分けても意見がそろいやすく、偏りを共有しうる。アプリが使う予定の OpenAI のモデルとは系統が違うので答え合わせの循環は避けるが、判定者の癖は正解に残る
- 判定者は職業名から仕事を自分で考えるので、職業の捉え方が判定者ごとにぶれうる。同じ立場でも科目の前半と後半を別の判定者が見るので、立場の中でも基準が少しずれうる
- 職業名だけを渡すと判定者は中心を控えめに付けるので、期待する科目は職業あたり 1〜6 と少ない。少ない職業では再現率が粗い数字になる(1 科目なら 0 か 1)
- 判定者が読むのは、科目名ごとに 1 クラスのシラバスの抜粋(概要、到達目標、各回のテーマのそれぞれ先頭だけ)で、検索は全クラスの全チャンクから最も近いものを使う。後ろの回や別のクラスでだけ職業に関わる内容を扱う科目は、判定では土台や関係なしになり、検索が上位に出しても数えられない。そのぶん再現率は低めに出うる
- 資料作りと集計はリポジトリに置かず、手順を指示文の文書に書くだけにした。1 学科・1 年度のうちは手で十分で、再判定のときに文書と食い違わないかは票と決定から評価データを確かめるテストで見る
- 判定者は関係なしの科目を書かないので、判定者が読み落とした科目と関係なしとした科目を区別できない。どの判定者も前半と後半の両方に票を入れていることまでしか確かめられない
- 判定に Claude のトークンを使う(188 科目 × 10 職業を 3 立場で判定し、1 回あたり 6 体)

## 再検討する条件

- 評価の数字と高橋さんの実感が食い違うとき(担い手の選択肢 3、高橋さんが全てを判定する形に寄せる)
- 学科や年度を増やすとき(同じ手順で判定し直す。資料作りと集計をスクリプトにしてリポジトリに置く)
- 判定者の多数決と高橋さんの決定が何度も食い違うとき(立場や指示文を見直す)
