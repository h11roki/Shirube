# 0024. Plan は同期の REST で作り、UUID の id で plans 表に JSONB で丸ごと保存する

- ステータス: 廃止(Superseded by 0029)
- 日付: 2026-10-16

## 文脈

ADR 0008 で、API は REST + OpenAPI 型生成、同期、Next.js Route Handler 経由とし、`POST /api/v1/plans` で道標を作って保存し、`GET /api/v1/plans/{id}` で再表示すると決めた。そのとき、後で非同期にできるよう Plan に id と status を持たせるとした。

フェーズ 6 で、職業から科目を選ぶ推薦(ADR 0023)と、推薦を学期に置く道標(ADR 0022)ができた。これを Plan として保存するために、保存の形、id、status、今の学期の決め方、保存するときの JSON への直し方を決める。今の学期は年度と月から決め、利用者が変えられる(ADR 0010、0022)。

LLM を含む生成は 10〜30 秒かかる。認証と Plan の持ち主はフェーズ 7 で入れる。

## 検討した選択肢

保存の形

1. plans 表に 1 つの Plan を 1 行で、学期と科目は JSONB に丸ごと入れる
2. 学期と科目を別の表にする(plans / semester_plans / plan_courses)

status

1. 今は持たない
2. 持つ(今は「完了」だけ)

id

1. UUID
2. 連番

今の学期の境目

1. 4〜8 月は春学期、9〜3 月は秋学期
2. 4〜9 月は春学期、10〜3 月は秋学期

JSON への直し方

1. infrastructure に手で書いた変換と、JSON の版番号
2. pydantic に domain の dataclass を渡して丸ごと直す

## 決定

高橋さんがどれも 1 を選んだ。status を持たないことは ADR 0008 の決定を変えるので、0008 のほかの決定をここに書き写して引き継ぐ。

API(ADR 0008 から引き継ぐ)

- REST + OpenAPI 型生成、同期。ブラウザ → Next.js Route Handler → FastAPI の順に呼ぶ
- `/api/v1` を接頭辞とし、`POST /api/v1/plans` が道標を作って保存し、`GET /api/v1/plans/{id}` で再表示する
- FastAPI の OpenAPI から openapi-typescript でフロントの型を生成する

Plan

- Plan は、id、作った条件、推薦(ADR 0023)、道標(ADR 0025)を持つ。作った条件は、入力した職業名、学科、時間割とシラバスの年度、始める学期(回生と学期)、学科で分かれたクラスの選択、1 学期の単位の上限
- id は UUID(v4)で、アプリが作る
- status は持たない。非同期にするときに、値と列を ADR で決めて足す
- 作る処理(CreatePlan)は、始める学期から 4 回生の秋学期までを残りの学期とし、そのどれかに開講される科目を候補に推薦し(ADR 0025)、その年度の時間割で残りの学期に置き、保存する。学科で分かれたクラスの選択は、LLM を呼ぶ前に確かめる。1 学期の単位の上限は `SEMESTER_CREDIT_LIMIT`(初期値 16)
- 今の学期は月で決める。4〜8 月は春学期、9〜3 月は秋学期。日付から学期を決める関数を domain に置き、API と CLI が今日の日付から既定値を出す。利用者は変えられる

保存

- plans 表に 1 つの Plan を 1 行で保存する。列は id、本文(JSONB)、作った時刻。持ち主の列はフェーズ 7 で足す
- 本文は版番号を持つ JSON で、infrastructure に手で書いた変換で domain と行き来する。版を上げずに JSON の形を変えない。知らない版は読まずに止め、読むときは値の型まで確かめる
- 版 1 の本文をテストの固定ファイルに置き、変換がその形を作ることと、その形から同じ Plan を読み戻せることを確かめる。置いたクラスは時間割の行(course_sections)と同じ変換で写すので、時間割の表の形を変えると、このテストが落ちて版の見直しに気づける
- 置いたクラスは、時間割の行を写して本文に持つ。時間割を年度ごとに入れ替えても(ADR 0014)、作った Plan は変わらない。推薦の科目と、秋学期に続く通年の授業は科目名で指し、読むときに引き直す
- Plan は作ったあと変えない

## 理由

- Plan は作った時点の結果で、丸ごと読み書きできれば足りる。表も移行も 1 つで済む(ADR 0014 と同じ考え方)
- 同期の今は status が常に「完了」で、値の変わらない列になる。非同期にするときに列を 1 つ足す移行で済む
- UUID は推測できないので、認可が入るフェーズ 7 までの間も、連番で他人の Plan を順にたどられない。アプリが作れるので、保存の前に id が決まる
- 秋学期の履修登録がある 9 月からは、秋学期を計画したい利用者が多い。授業の終わった 8 月を春に入れても、利用者が変えられる
- 手で書いた変換なら、domain の名前を変えても保存の形は変わらない。版番号があれば、古い Plan を読めなくする変更に気づける
- ADR 0008 から: バックエンドを非公開ネットワークに置け、CORS が要らない。型生成で API の契約のずれをビルド時に見つけられる

## 受け入れたトレードオフ

- 科目ごとの集計(どの科目がよく推薦されるかなど)を SQL でしにくい
- 変換のコードが増え、domain の型を変えるたびに変換とその版を直す
- UUID は URL が長い
- 2〜3 月は授業の終わった秋学期が既定になる。次の春学期から計画するには、利用者が回生と学期を変える
- 非同期にするときに status の列を足す移行が要る
- 置いたクラスを写すので、時間割の誤りを直しても、作った Plan には反映されない
- ADR 0008 から: 処理中は画面が待ち、ロードバランサ経由ではタイムアウトに当たりうる。Route Handler の分だけ往復が 1 段増える

## 再検討する条件

- 推薦された科目の集計を SQL で取りたくなったとき
- 生成を非同期にするとき(ALB や API Gateway の背後でタイムアウトが起きた、進捗を見せたい)
- 時間割の誤りの修正を、作った Plan にも反映したくなったとき
