# 0088. 理由の文を、柱は職業とのつながり、礎は柱の前提で 3 段に判定し、Claude の正解で確かめた gpt-5.4-nano の判定器で測る

- ステータス: 承認(判定器は、gpt-5.4-mini に替えて整えても確かめる用の κ が 0.54 で 0.6 に届かず、採らなかった。experiment reasons は作らない。2026-11-04、PR #98)
- 日付: 2026-11-04

## 文脈

- 選び直し(ADR 0018、0023、0080)は、選んだ授業ごとに 80 字以内の理由を書き、学生は切符でそれを読む。指示文は、柱(中心)の理由には「その職業を目指す学生がなぜ取るべきか」を、礎(土台)の理由には「つながる柱の授業のどの内容の前提になるか」を書かせている
- 評価(ADR 0017、0048、0053)が測っているのは、どの授業を選んだかだけで、理由の文は測っていない。README にも「理由の文の良し悪しは、まだ測っていません」と書いている
- 実験の結果の JSON には、理由の文が全て残っている。今の本番と同じ設定の `eval/runs/20261031-120812-selection-min-votes-before.json`(開発用 50 職業、1 回)には、道標に並ぶ理由が 476 件(柱 283、礎 193。中心につながらず外した礎は道標に並ばないので除く)あり、80 字を超えるのは 4 件だけ
- 読んでみると、「IT エンジニアの実務に直結する」「AI を含む開発の土台になる」のように、職業のどの仕事に効くかが分からない柱の理由が目立つ
- 理由の文は流すたびに変わるので、授業の判定(ADR 0017)のように一度付けた正解を使い回せない。指示文やモデルを替えたときに測るには、自動の判定が要る
- 高橋さんは、LLM の出力の質を自分のデータで測ることを、評価の取り組みとして示したい(ADR 0074)

## 検討した選択肢

何を測るか(いくつでも)

1. 抜粋にあることだけを言っているか(選び手に渡した抜粋に無いことを言っていないか)
2. 柱の理由の、職業とのつながり
3. 礎の理由が、つながる柱のどの内容の前提かを言えているか
4. 書き方の決まり(80 字以内、英語の語、抜粋の写し)

誰が判定するか

1. Claude のサブエージェント 3 体が約 150 件に正解を付け、gpt-5.4-nano の判定器を作って正解との一致を確かめてから、全件を判定し、実験の道具にも入れる
2. Claude のサブエージェント 3 体が 476 件全部を一度だけ判定する
3. gpt-5.4-nano の判定器だけで、正解と突き合わせない

職業とのつながりをどの理由で測るか

1. 柱の理由だけ
2. 柱と礎の両方

段の数

1. 3 段(具体的 / ぼんやり / 無い)
2. 2 段(言えている / 言えていない)

判定器を採る条件

1. 正解を半分に分け、片方だけを見て判定器の指示文を整え、もう片方で一度だけ Cohen の κ を測り、0.6 以上なら採る
2. 正解の全部を見て整え、一致率 80% 以上なら採る

実験の道具への入れ方

1. 別のコマンド(`experiment reasons`)に結果の JSON を渡して判定する。2 つ渡すと差も出す
2. `experiment run` と `pair` で毎回判定する

## 決定

高橋さんが、測るものは 2 と 3、判定は 1、つながりは 1(柱だけ)、段は 1(3 段)、採る条件は 1、入れ方は 1 を選んだ。

判定の決まり(正解と判定器で同じ)

- 柱の理由は「職業とのつながり」を判定する
  - 具体的: 職業の仕事の中身(する作業、作るもの、扱う対象、使う技能)を 1 つ以上挙げ、授業で学ぶことがそこにどう使われるかが分かる
  - ぼんやり: 職業や分野、「実務」「業務」には触れるが、「役立つ」「直結する」「必須」「基礎になる」だけで、仕事のどこにどう使うかが分からない
  - 無い: 授業で学ぶことの紹介だけで、職業にも仕事にも触れていない(授業で身につく技能を挙げるだけで、職業の仕事に結び付けていないものを含む)
- 礎の理由は「柱の前提」を判定する
  - 具体的: つながる柱の授業(科目名か、その授業で扱う内容)を挙げ、この授業のどの内容が、柱のどの内容の前提になるかが分かる
  - ぼんやり: 柱の授業や分野には触れるが、「基礎になる」「理解に役立つ」だけで、柱のどの内容の前提かが分からない
  - 無い: 柱の授業にも、その内容にも触れていない(職業に触れるだけのものを含む)
- 判定に渡すのは、職業(選び手に渡したのと同じ、読み取りの解釈と前提)、柱か礎か、授業名、礎ならつながる柱の授業名、理由の文だけ。シラバスの抜粋は渡さない。言っていることがシラバスに本当にあるか、長さ、言い回しは判定しない(選ばなかった 1 と 4)

正解(Claude のサブエージェント)

- 対象は上の 476 件。職業を乱数(種 0)で 25 職業ずつの 2 つに分け、片方を「整える用」、もう片方を「確かめる用」にする。同じ職業の理由は似るので、件ではなく職業で分ける
- それぞれから柱 38 件、礎 37 件を乱数で取り、計 150 件にする
- 3 体のサブエージェントに、150 件を混ぜた順に、判定の決まりと同じ指示文で独立に判定させる。立場は分けない(授業の判定と違い、立場で答えが変わる問いではなく、文が決まりに当たるかを見る問いのため)。1 件ごとに短い根拠を先に書かせてから段を付けさせる
- 正解は 3 票の中央値(無い < ぼんやり < 具体的)にする。2 票がそろえばその段になり、3 票が割れればぼんやりになるので、人が決める件は出ない
- 3 体どうしの一致を Fleiss の κ で出す。これが判定器の目安の上限になる
- 指示文、取り方、まとめ方は `backend/eval/reason-judge-prompt.md` に、票と根拠と正解は `backend/eval/reason-judgments.json` に残す。取り出し、まとめ、確かめは CLI で行い、同じ結果の JSON と種から同じ 150 件を取り直して、残した正解がそれと合うかを確かめられるようにする。まとめるときは書く先を毎回書かせ、残した正解を黙って上書きしない

判定器(gpt-5.4-nano)

- 1 件ずつ呼び、構造化出力で根拠(短い文)を先に、段をあとに書かせる。指示文は判定の決まりと同じ定義から始め、整えるのは言い回しと例だけで、段の定義は変えない。例は整える用の件からだけ取る
- 整える用の 75 件で、正解との一致を見て指示文を整える。確かめる用の 75 件は、整え終えてから一度だけ流し、正解との Cohen の κ(重みなし)と、取り違えの表を出す
- κ が 0.6 以上なら採る。届かなければ、金額を添えて聞いてから gpt-5.4-mini で同じ指示文を流す(モデルを替えるだけで指示文は整え直さないので、確かめる用を 2 度見ることは README と記録に書く)。mini でも届かなければ、判定器は採らず、正解の 150 件の数字だけを記録に残す
- モデルは設定 `REASON_JUDGE_MODEL`(既定 gpt-5.4-nano)、指示文の指紋を判定の結果に残す

実験の道具

- `experiment reasons <結果の JSON> [<後の結果の JSON>]` で、結果の理由を判定器で判定し、柱と礎それぞれの 3 段の割合を出す。判定は結果の JSON の横に `-reasons.json` として残し、同じモデルと指示文で判定済みならそれを読んで API を呼ばない
- 2 つ渡すと、ねらいの指標(柱と礎それぞれの「具体的」の割合)の差を、`experiment compare` と同じ職業を選び直すブートストラップと並べ替え検定(ADR 0053、0055)で出す
- `--budget`(円)を超えたら次の判定を始めずに止める
- 判定器と正解の一致は `experiment reason-agreement --split tune|check` で出す

進め方

- この ADR の PR では、正解(Claude の判定)と、取り出しとまとめの CLI までを入れる。OpenAI の費用はかからない
- 次の PR で、判定器、`reason-agreement`、`reasons` を入れ、判定器を整えて確かめ、476 件を判定する。整える試しと確かめと全件で、nano なら合わせて 50 円ほどの見込みで、流す前に金額を添えて聞く
- 測ったら、`docs/evaluation-log.md` と README の「理由の文の良し悪しは、まだ測っていません」を書き換える。理由を直すのは、その数字を見てから別に決める

## 理由

- 柱の理由が職業のどの仕事に効くかを言えていないと、学生は「なぜ取るか」に納得できない。礎の理由は柱への乗り換えの説明なので、柱のどの内容の前提かが言えているかを見るのが、指示文の求めと 1 対 1 になる
- 3 段にすると、「役立つ」「直結する」で終わる文を分けて数えられ、直すときの的が見える
- 理由は流すたびに変わるので、指示文を替えたあとも測るには自動の判定器が要る。判定器が正しいかを正解との一致で確かめておけば、その数字を信じる根拠になる
- 判定器の指示文を確かめる用の件を見ずに整えれば、正解に合わせ込んだだけの一致にならない(ADR 0067 で開発用と確かめ用の職業を分けたのと同じ考え)
- 3 票の中央値なら、3 段の 3 票はいつも 1 つの段に決まり、作者が決める件を作らずに済む
- 判定に抜粋を渡さなければ、入力が短く、1 回の判定が安い。測るのは文の書き方の中身で、事実との照合ではない

## 受け入れたトレードオフ

- 言っていることがシラバスに本当にあるか(作り話)は測らない。指示文は「抜粋に書いていないことは書きません」と求めているが、守られているかは分からないまま
- 正解は人ではなく Claude が付ける。判定者の癖は正解に残る(ADR 0017 と同じ)。アプリの LLM(OpenAI)とは系統を分けている
- 確かめる用は 75 件で、κ の幅は広い。0.6 の線の近くでは、採るかの判断が揺れうる
- 判定するのは 1 回分の結果だけで、同じ設定で流し直したときの揺れは、この PR では分からない
- 礎の理由が職業に触れないことは問題にしない。学生が礎の切符だけを読むと、職業との関係は乗換の欄の柱をたどらないと分からない

## 再検討する条件

- 判定器の κ が 0.6 に届かなかったとき(判定の決まりを見直すか、判定を Claude に戻すか)
- 3 体の Claude の一致(Fleiss の κ)が 0.4 を下回ったとき(判定の決まりがあいまいなので、決まりから直す)
- 理由の文が抜粋に無いことを言っている例が見つかったとき(測るものに 1 を足す)
- 指示文かモデルを替えて理由を直すとき(`experiment reasons` で前と後を比べ、測る前にねらいと採る条件を ADR に書く)
- 礎の切符だけでは職業とのつながりが分からない、と利用者から言われたとき(礎にも職業とのつながりを測る)
