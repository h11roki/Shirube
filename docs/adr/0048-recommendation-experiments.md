# 0048. 推薦の評価を通しの実験として回数を決めて流し、精度・揺れ・費用・時間を JSON に残して比べる

- ステータス: 承認
- 日付: 2026-10-23

## 文脈

推薦(職業の読み取り → 検索 → 選び直し)の評価は 2 つの CLI に分かれている。`evaluate` は検索の再現率 @10/@20 を(ADR 0016、0017、0018)、`evaluate_selection` は手書きのスキルに固定して、選び直しの結果を判定の票と比べる(ADR 0023)。どちらも結果を画面に出すだけで、次のことができない。

- 揺れ: 同じ条件でも結果は回ごとに変わる(ADR 0020 では、関係なしの割合が 4 回で 17〜26%)。今は手で何回か流し、範囲を ADR に書いている。改善の差が揺れより大きいかを、決まった方法で確かめられない
- 通しの評価: 段ごとに片方を固定して測っていて、推薦全体の質は測っていない(ADR 0020)。職業の読み取りの揺れが検索と選び直しに与える影響が分からない
- 費用と時間: トークン数も費用も待ち時間も記録していない。精度を上げる手(モデルを替える、何回か選ばせる)が、費用と時間をどれだけ増やすかを比べられない
- 結果の保存と比べ方: 比べるのは ADR の表で手作業。どのモデル、どの指示文、どの commit の結果かを残していない

推薦の精度を上げていくには、変更の前と後を、揺れと費用と時間も含めて同じ物差しで比べる仕組みが要る。

## 検討した選択肢

1. 今の 2 つの CLI に、回数と JSON の出力を足す。段は別々のままで、通しの評価にならない
2. 通しの実験を流す CLI を新しく作り、1 回の推薦から検索と選び直しの指標を両方取る。今の 2 つの CLI は残す
3. 外部の評価サービス(LangSmith、Ragas など)を使う。判定データの形(3 つの立場の票と多数決)は独自で、合わせる手間がかかる。データを外に出し、使う量でお金がかかる

## 決定

選択肢 2 にする。

- `python -m app.presentation.cli.experiment run --label <名前> --repeat <回数>` で、評価データの 10 職業それぞれに推薦を指定の回数だけ流す。候補は今の評価と同じく 1〜4 回生の全学期。職業の読み取りは、既定では LLM(本番と同じ通し)、`--profiles handwritten` で評価データの手書きのスキルに固定する(ADR 0023 の数字と比べるため)
- 1 回の推薦ごとに次を取る
  - 職業の読み取り: 解釈、前提、スキル(解釈は検索文の 1 行目にも選び直しの指示にも入るので、読み取りの揺れが後ろの段にどう効いたかを追えるように残す)
  - 検索: 期待する科目の再現率 @10/@20(今の `evaluate` と同じ)と、選び直しに渡した候補(`SELECTION_CANDIDATE_LIMIT` 件)の再現率。@20 を候補から測るので、候補の数が 20 より少ない設定では流さない。全職業の平均は職業ごとの再現率の平均
  - 選び直し: 中心の適合率、期待する科目を中心に選んだ割合、選んだ科目のうち関係なし、1 職業に選んだ数(中心、土台)。全職業の合計で割る(今の `evaluate_selection` と同じ)。中心も選んだ科目も無い回の割合は、0 ではなく未定義として平均に入れない(`evaluate_selection` の「-」と同じ)
  - 費用: LangChain の使用量の記録から、モデルごとの入力・キャッシュした入力・出力のトークン数を取る。料金表(2026 年 10 月の OpenAI の料金、1 ドル 150 円)で円にする。埋め込みの費用は 1 回 0.01 円未満なので数えない
  - 時間: 段ごとの秒数(職業の読み取り、検索、選び直し)
- 回ごとの値から、指標ごとに平均、標本標準偏差、最小、最大を出す。揺れは、同じ職業の回どうしで、選んだ科目の集合の Jaccard 係数(重なり)を全ての組で平均し、職業で平均する(選んだ科目全体と、中心だけ)
- 結果は `backend/eval/runs/<日時>-<名前>.json` に、設定(モデル、候補数、指示文の指紋、commit、評価データの指紋)、職業ごとの生の出力(読み取り、候補の順位、選んだ科目と判定と理由、中心につながらず外した土台とその理由)、指標、費用、時間を残す。手書きのスキルで流すときは、使わない読み取りのモデルと指示文の指紋を記録しない。設定と commit は流し始める前に記録する。commit していない変更があれば、その差分の指紋を commit に付ける(指示文の指紋は指示文だけで、抜粋の長さやスキーマの説明の変更は差分の指紋で分かる)。README や ADR に数字を載せる回はコミットする
- `python -m app.presentation.cli.experiment compare <A> <B>` で、2 つの結果の指標を並べ、差と、差が揺れ(2 つの標本標準偏差の大きい方)を超えるかを示す。採点した回が 2 回に満たない結果では判断しない。設定の違い(結果に効かない費用の上限は除く)と、止まった理由と失敗の数も並べる
- 費用の上限を `--budget`(円、既定 100)で決め、超えたら次の推薦を始めず、そこまでの結果を途中で止めたと記して残す。料金表に無いモデルでは上限を守れないので始めない
- 本番で 1 件の道標の失敗にする外部のサービスの失敗(埋め込み、職業の読み取り、選び直し、答えの食い違い。`BuildPlans` の `UPSTREAM_ERRORS`)は、その推薦の失敗として記録して続ける。3 回続けて失敗したら止める(障害や指示文の誤りのときに払い続けないため)。DB の失敗、Ctrl-C、SIGTERM、SIGHUP、思わぬ失敗(トレースバックを出す)で止まったときも、そこまでの結果を残す。推薦が全て失敗した結果も、集計なしで残す
- 指標の回ごとの値は、全職業の推薦がそろった回だけで出す(途中で止まった回や失敗のあった回を混ぜると、平均と揺れがずれる)。そろった回が無いときは全ての回で出し、そろった回と採点した回の数を結果に残す。1 回の推薦あたりの費用は、失敗した推薦の使用量も数えて割る。実験全体で使った費用は外側でも数え、途中で止めた推薦の分も入れる
- 推薦の各段(読み取り、検索、選び直し)の作りは変えない。使用量の記録は LangChain の仕組み(`get_usage_metadata_callback`)で外から取り、application はポート(`UsageMeter`)にだけ頼る

## 理由

- 1 回の推薦から検索と選び直しの指標を両方取るので、職業の読み取りの揺れが後ろの段にどう効くかまで見える
- 指標の定義を今の 2 つの CLI に合わせたので、ADR 0018、0020、0023 の数字と比べられる
- 揺れを数で持つので、「差は揺れの範囲」(ADR 0021)を決まった方法で判断できる
- 精度、揺れ、費用、時間を同じ結果に残すので、精度を上げる手の値段が分かる。本番で、上限のある費用(ADR 0038)の中でどの手を選ぶかを決められる
- JSON と設定を残すので、あとから同じ物差しで比べ直せる

## 受け入れたトレードオフ

- 評価データは 1 学科、10 職業、期待する科目 33 で小さい。数ポイントの差は揺れに埋もれる
- 正解は LLM(Claude)の 3 つの立場の判定の多数決で、人の判断そのものではない(ADR 0017)
- 1 回の実験(10 職業 × 3 回)に 25 円ほどかかる(1 件 0.8 円)。CI では流さず、変更のたびに手で流す
- 料金表はコードに書くので、料金が変わったら直す
- 候補は全学期で、本番(残りの学期、取った授業を除く)と少しずれる
- 回数は既定で 3 回なので、標本標準偏差は粗い。「揺れより大きい」は目安で、検定ではない
- 出力が長さの上限に達した答えや、内容のフィルタで止められた答えは、LangChain の使用量の記録に残らないので費用に数えない(出力の上限は付けておらず、今の指示文では起きていない)
- DB の中身(シラバス、チャンク、埋め込み)の指紋は残さない。取り込み直しや埋め込み直しのあとは、前の結果と比べる前に基準を測り直す
- 失敗した推薦は、失敗の文と使用量だけを残し、途中までの読み取りや候補は残さない

## 再検討する条件

- 評価データの職業や学科を増やすとき
- 実験を定期的に(CI や毎晩)流したくなったとき
- OpenAI の料金かモデルが変わったとき
- OpenAI の service tier(priority、flex)を使うとき(キャッシュした入力の記録のされ方と料金が変わる)
