# 0018. 職業は LLM がスキルに直し、検索の上位を LLM が読み直して科目と理由を選ぶ

- ステータス: 承認(前提を書く場合は ADR 0032 で広げた。`evaluate --skills llm` を解釈した職業名とスキルの検索文で測るようにしたことは ADR 0065)
- 日付: 2026-10-16

## 文脈

フェーズ 5 では、利用者が入力した職業から必要なスキルを出し、関連する授業を選んで、取るべき理由を付ける。ADR 0016 と 0017 の評価で、手書きのスキルを使った検索の再現率は @10 が平均 0.93、@20 が平均 1.00 だった。一方で、上位 10 件(10 職業で 100 件)のうち 23 件は、判定で 3 体とも関係なしとした科目だった。正解はほぼ拾えるが、関係の薄い科目も上位に混ざる。

利用者が入力する職業名は評価データのように具体的とは限らない。「コンサルタント」のように、IT 系か経営・戦略系かで必要な科目が大きく変わる名前もある。

時間割の生成(フェーズ 6)はまだ無く、ADR 0008 の `POST /api/v1/plans` は時間割を含む Plan を保存して返す形で決まっている。

## 検討した選択肢

授業の選び方

1. ベクトル検索の上位 N 件を LLM がシラバスの抜粋を読んで選び直し、取るべき理由も同時に書く
2. 検索の上位をそのまま使い、LLM は理由だけを書く
3. 検索を使わず、候補の全科目を LLM に読ませる

検索文

1. 職業名と LLM が出したスキルをつなげて 1 回検索する(評価と同じ形)
2. スキルごとに LLM が授業概要風の文を書き、スキルごとに検索して合わせる

解釈が割れる職業名

1. LLM が電子情報工学科の学生に多い解釈を 1 つ選び、その前提を結果に書く
2. 解釈の候補を返し、利用者に選んでもらってから組む

フェーズ 5 の範囲

1. 推薦のユースケース、試すための CLI、評価まで。Plan の表と API はフェーズ 6 で時間割と一緒に作る
2. フェーズ 5 で `POST /api/v1/plans` も作り、スキルと科目と理由を保存して返す。フェーズ 6 で時間割を足す

## 決定

授業の選び方は選択肢 1、検索文は選択肢 1、解釈が割れる職業名は選択肢 1、範囲は選択肢 1。

- 職業名を LLM に渡し、構造化出力で「解釈した職業名」「解釈が割れたときの前提(割れなければ無し)」「必要なスキル 3〜6 個」を受け取る
- 検索文は、解釈した職業名とスキルを改行でつないだもの。ADR 0016 の評価の検索文と同じ形にし、手書きのスキルとの差をそのまま比べられるようにする
- 検索の上位 N 件(設定値)のシラバスの抜粋を LLM が読み、その職業に関係する科目だけを選んで、科目ごとに取るべき理由を書く。関係する科目が少なければ少ないまま返し、関係の薄い科目で埋めない。理由はシラバスの中身を自分の言葉でまとめ、本文を写さない
- LLM はアプリケーションのポート(Protocol)で受け、OpenAI のチャットモデルを LangChain の構造化出力で呼ぶ実装を置く。モデル名は設定値(`CHAT_MODEL`)で、スキルを出す段の初期値は gpt-5.4-mini。選び直しの段のモデルは、その実装のときに評価データで比べて決める
- 評価は 2 段で行う。スキルは `evaluate --skills llm` で、評価データの職業名はそのままにスキルだけを LLM の出力に替えて再現率を比べる(LLM が解釈した職業名は使わず、スキルの差だけを見る)。選び直しは、選んだ科目が判定(`backend/eval/judgments.json`)で期待する科目・土台・関係なしのどれにあたるかの割合と、期待する科目の取りこぼしを出す
- フェーズ 5 では Plan の表と API を作らない。フェーズ 6 で時間割と一緒に作り、ADR 0008 の API の形は変えない

## 理由

- 評価で上位に関係の薄い科目が 2 割混ざった。LLM がシラバスを読んで選び直せば、道標に関係の薄い科目を並べずに済み、理由も読んだ中身に基づいて書ける
- 全科目を読ませると入力が 5 倍以上になり、他学部に広げるとさらに増える。検索で絞ってから読ませれば、入力の大きさは候補の数によらない
- 検索文を評価と同じ形にすると、LLM のスキルで検索の質が落ちていないかを、今の基準値と同じ条件で確かめられる
- 前提を示して 1 回で返せば API も画面も 1 段で済み、意図と違えば利用者が職業名を具体的にして作り直せる
- Plan は時間割を含めて完成する。表と応答の形を 1 回で決めれば、フェーズ 6 で作り直さずに済む
- スキルを出す段はモデルを評価データで比べた。スキルだけを替えた再現率@10 は gpt-5.4-mini が 3 回で 0.93〜0.95、gpt-5.4-nano が 0.90〜0.92 で、手書きのスキル(0.93)とほぼ同じだった。@20 は mini が 3 回とも 1.00、nano は 1 回が 0.95。gpt-5-mini は、解釈した職業名も検索文に入れていた形で 1 回だけ測り、@10 が 0.82 で 1 職業に約 9 秒かかったので外した。曖昧な職業名 4 件(コンサルタント、エンジニア、公務員、ゲームクリエイター)で前提を書いたのは mini が 4 件、nano が 1 件で、nano はコンサルタントを前提なしに経営コンサルタントと解釈した。前提を示す決まりを守れる mini にした。1 回の費用は mini で約 0.15 円、nano で約 0.04 円

## 受け入れたトレードオフ

- LLM を 2 回(スキル、選び直し)と埋め込みを 1 回呼ぶので、1 回の生成に 10〜20 秒ほどかかりうる。費用は軽量モデルで 1 回あたり数円
- LLM の出力は呼ぶたびに少し変わるので、同じ職業でも結果が揺れる
- 検索文が 1 つなので、幅の広い職業では一部のスキルに関係する科目を取りこぼしうる
- 解釈を LLM が決めるので、利用者の意図と違う解釈で組むことがある。前提を示すことで気づけるようにする
- API を触れるのはフェーズ 6 からになる

## 再検討する条件

- LLM のスキルでの再現率が手書きのスキルより大きく下がるとき(検索文の選択肢 2 を試す)
- 選び直しで期待する科目を落とすことが多いとき(N を増やすか、選ぶ基準の指示を見直す)
- 1 回の生成が画面で待てないほど遅いとき(モデルを替えるか、生成を非同期にする)
- 他学部に広げて候補が増え、上位 N 件では関係する科目が収まらないとき
