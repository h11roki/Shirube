# 0103. 細かい職種を広く読むときも、仕事の向きを残した職業名にし、「ITエンジニア」にまとめない

- ステータス: 承認(1 回目は関係なしが差ありで増えて採らず、文面を直して交互に流した 2 回目で採る条件を満たしたので、組み込みの指示文を替えた。末尾の追記)
- 日付: 2026-11-13

## 文脈

- ADR 0032 で、学科の授業に無い応用分野や道具で決まる細かい職種は、学科の授業で備えられる広い職業として読むことにした。指示文には例として「Webエンジニアは ITエンジニアと読む」と書いた
- 2026-11-04 の実験(開発用 50 職業の 1 回目、`20261104-210717-reason-wording-after.json`)では、9 職業が「ITエンジニア」と読まれた: Web エンジニア、スマートフォンアプリ開発エンジニア、クラウドエンジニア、自然言語処理エンジニア、検索・推薦システムのエンジニア、金融系システムエンジニア、テック系スタートアップの起業家、システムエンジニア、ソフトウェア開発エンジニア。制御の 3 職業(EV・蓄電池、空調・家電、工場の自動化)は「制御エンジニア」と読まれた
- 解釈した職業名は検索文の先頭に入る(ADR 0018、0063)。違う職種が同じ名前になると、検索の候補の差はスキルにしか出ず、道標が似る。ADR 0032 の受け入れたトレードオフに書いたとおりで、画面の行き先は入力した職業名に戻したが(ADR 0100)、推薦の中身はまとめた職業のまま
- 評価データの期待する科目は職業ごとに判定したもので(ADR 0017、0054)、例えばクラウドエンジニアと自然言語処理エンジニアでは違う。まとめると、その違いを拾えない
- 高橋さんが、広く読むのは続けたまま、まとめ先を「ITエンジニア」にせず、専門の向きを残すことを選んだ。測り方は、評価データにすでにある細かい職種で測ることにした

## 検討した選択肢

1. 広く読むのは続け、解釈した職業名に元の仕事の向き(扱う対象や技術の領域)を残す。「ITエンジニア」のように向きの消える名前にしない
2. 読み替えない。解釈は入力した職業名のままにし、スキルだけ授業の分野の名前で書く(ADR 0032 の選択肢 3)
3. 解釈は広いまま、入力した職業名も選び直しに渡す

## 決定

高橋さんが 1 を選んだ。

- 読み取りの指示文の解釈の決まりを替える。細かい職種を学科の授業で備えられる職業として読むときも、元の職業の仕事の向きを職業名に残し、「ITエンジニア」「制御エンジニア」のように、違う職種が同じ名前になるまとめ方をしない。例は「Webエンジニア」→「Web システムのソフトウェアエンジニア」、「クラウドエンジニア」→「ネットワークとサーバー基盤のエンジニア」にする。前提の例も合わせる
- スキルの決まり(授業の分野の名前で書く)、前提を書く決まり、学科の授業がそのまま備える職業はそのまま読む決まりは変えない

測り方

- 読み取りの指示文は pair で切り替えられないので、今の main で `experiment run --label reading-before --budget 130` を開発用 50 職業に 3 回流し、続けて指示文を替えた版で `--label reading-after` を流す(合わせて約 260 円)。流した時刻の揺れが差に入る、断りの付いた比べとして読む
- `experiment compare` で選ぶ授業の指標を比べ、`experiment analyze` で、期待する科目をどの段で落としたかを前と後で並べる

採る条件(測る前に決める)

- ねらい: 「ITエンジニア」か「制御エンジニア」と読んだ推薦の数が、3 回の合計で前の半分以下になる
- 条件: `experiment compare` で、選び直しに渡した候補の再現率と、期待する科目を中心に選んだ割合が、下がる向きで差あり(p < 0.05)にならず、選んだ科目のうち関係なしが増える向きで差ありにならない
- 満たせば指示文を替え、確かめ用 20 職業で前と後を 1 回ずつ流して(`experiment run --dataset eval/heldout/occupations.json --judgments eval/heldout/judgments.json`、合わせて約 90 円)、平均だけを見る。確かめ用では、関係なしと期待する科目を中心に選んだ割合の点の推定が、悪い向きに 5 ポイントより動かなければ採る。満たさなければ前の文面に戻し、結果を評価の記録に残す
- 採ったら、ADR 0089 の指示を混ぜた職業名 3 件を `recommend` で流し直して、0089 に追記する

## 理由

- ADR 0032 の良さ(授業の分野の名前で検索し、学科の授業とかみ合う)はスキルの決まりが担っている。職業名に向きを残しても、スキルは授業の分野の名前のまま
- 検索文の先頭に向き(Web、クラウド、言語処理など)が入れば、職種ごとに候補が変わり、期待する科目の違いを拾える
- 2 は ADR 0032 の前の「Webエンジニアで 2 科目しか選ばれない」が戻るおそれがある。3 は検索の候補が変わらないので、候補に無い授業は選べない

## 受け入れたトレードオフ

- 職業名が少し長くなる。画面の行き先は入力した職業名なので(ADR 0100)、長くなるのは板の上の〔読み替えた職業 …〕だけ
- どこまでを向きとして残すかは LLM の判断で揺れる
- 読み取りの指示文が変わるので、残した推薦は当たらなくなり(ADR 0092)、次に作るときに作り直される

## 再検討する条件

- 採る条件を満たさなかったとき
- 向きを残した名前で、検索の候補が学科の授業から外れる職種が出たとき(analyze の読み取りで落とした数で見る)

## 追記: 1 回目の比べ(2026-11-13)

`reading-before`(今の main)と `reading-after`(替えた文面)を run で続けて流した(合わせて 238.3 円)。

| 指標 | 前 | 後 | 差 |
|---|---|---|---|
| ITエンジニアか制御エンジニアと読んだ推薦(150 回中) | 36 | 3 | ねらいを満たす |
| 選び直しに渡した候補の再現率 | 92.0% | 90.1% | はっきりしない(p = 0.434) |
| 期待する科目を中心に選んだ割合 | 70.4% | 71.5% | はっきりしない(p = 0.769) |
| 選んだ科目のうち関係なし | 13.1% | 17.5% | 差あり(+4.3 ポイント、区間 +1.2〜+7.7、p = 0.012) |

関係なしが増える向きで差ありになり、採る条件を満たさなかったので、組み込みの文面は前に戻した。

- 前にまとめて読んでいた 11 職業(Web、スマートフォンアプリ、クラウド、自然言語処理、検索・推薦、金融系、ソフトウェア開発、システムエンジニア、EV・蓄電池、空調・家電、工場の自動化)の関係なしは 3 回の合計で 25 件から 29 件で、大きくは動いていない
- 増えたのは、プロダクトマネージャー(10 → 25 件)、IT 企業のソリューション営業(3 → 12 件)、IT コンサルタント(4 → 12 件)のような営業と企画の職業。前は「ITプロダクトマネージャー」のように技術の領域が付いて読まれていたのが、替えた文面では入力した名前のまま読まれ、技術の授業と結びつきにくくなった
- 読み方の変わらなかった職業でも 15.5% → 17.8% で、続けて流した時刻の揺れも入っている

## 追記: 2 回目の比べの作りと採る条件(2026-11-13、流す前に書く)

高橋さんが、文面を直し、交互に流して測り直すことを選んだ。

- `experiment pair` で読み取りの指示文も切り替えられるようにする。`OCCUPATION_PROMPT=<ファイル>` を `SELECTION_PROMPT`(ADR 0068)と同じ決まり(UTF-8、前後の空白を除く、無い・読めない・空・組み込みの書き方が残っていれば流す前に断る、結果の設定に文面の指紋を残す)で読み、本番の設定にはしない。読み取りを使わない `--profiles handwritten` では断る
- 文面は 1 回目の文面に、技術を使う側の職業(営業、企画、コンサルタント、起業家など)は、学科の技術のどの領域を扱う職業かを職業名に入れる、と足す(例: 「プロダクトマネージャー」は「IT製品のプロダクトマネージャー」)
- `experiment pair --label reading-direction --after OCCUPATION_PROMPT=<後の文面> --budget 320` で、開発用 50 職業に前(組み込みの文面)と後を交互に 3 回ずつ流す(約 300 円)

採る条件は 1 回目と同じにする。

- ねらい: ITエンジニアか制御エンジニアと読んだ推薦の数が、前の側の半分以下
- 条件: `experiment compare` で、選び直しに渡した候補の再現率と、期待する科目を中心に選んだ割合が下がる向きで差ありにならず、関係なしが増える向きで差ありにならない
- 満たせば組み込みの文面を後の文面に替え、確かめ用 20 職業で同じ pair を 1 回ずつ流して(約 40 円)、平均だけを見る。関係なしと期待する科目を中心に選んだ割合の点の推定が、悪い向きに 5 ポイントより動かなければ採る。満たさなければ前の文面のままにし、評価の記録に残す

## 追記: 2 回目の比べの結果(2026-11-13)

`reading-direction`(開発用 50 職業、前と後を交互に 3 回ずつ、299.8 円)と、確かめ用 20 職業の同じ pair(1 回ずつ、43.6 円)を流した。数字は `docs/evaluation-log.md`。

- ねらい: ITエンジニアか制御エンジニアと読んだ推薦は、150 回のうち 48 回から 0 回になった
- 条件: 候補の再現率 87.2% → 87.1%、期待する科目を中心に選んだ割合 70.4% → 71.5%、関係なし 16.6% → 15.7% で、どれも差なし。確かめ用は期待を中心に 74.1% → 84.5%、関係なし 13.7% → 16.8%(+3.1 ポイントで 5 ポイント以内)
- 採る条件を全て満たしたので、組み込みの指示文を後の文面に替えた
- 条件に無かった副作用として、1 職業に選んだ土台が 3.52 → 4.09 で差ありで増えた
- ADR 0089 の指示を混ぜた職業名 3 件を流し直した(0089 の追記)
