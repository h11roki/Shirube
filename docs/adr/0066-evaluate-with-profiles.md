# 0066. 検索の評価は、手書きか LLM の読み取りから推薦と同じ検索文を作って測る

- ステータス: 承認
- 日付: 2026-10-26

## 文脈

- `evaluate --skills llm` は、LLM の出したスキルを評価データの職業名と組み合わせて検索文を作っていた(ADR 0018 のころは解釈が無かった)。推薦は解釈した職業名とスキルで検索文を作る(ADR 0032)ので、読み取りの解釈が替わる変更を測れない(ADR 0032 にも書いた)。ADR 0065 で読み取りの指示文を測る前に、高橋さんがこれを先に直すことを選んだ
- 手書きのスキルの評価は、`EvaluationCase` が評価データの職業名とスキルから自分で検索文を作っていた。選び直しの評価と実験の `--profiles handwritten` は、手書きのスキルを `HandwrittenProfiles` で読み取り(`OccupationProfile`)の形に包み、その検索文を使う。手書きの検索文の作り方が 2 つあり、推薦の検索文が変わると評価だけずれうる
- `evaluate --skills llm` は、50 職業の読み取りを済ませてから DB を確かめていた。埋め込みが無いときや期待する科目名が候補に無いときも、読み取りの費用(約 7.5 円)を使ってから止まる

## 検討した選択肢

1. 検索の評価に読み取りの元(`HandwrittenProfiles` か LLM の読み取り)を渡す。評価は候補と科目名を確かめてから職業を読み取り、読み取りの検索文で検索する。検索文は推薦と同じ `OccupationProfile.query` だけで作る
2. 評価の職業に解釈の文字列か読み取りを持たせる。差分は小さいが、解釈の確かめと検索文の作り方を読み取りと二重に持ち、スキルも 2 か所に持つ
3. 直さずに、`--skills llm` はスキルだけの評価だと書いておく

## 決定

1 にする(ADR 0065 の測り方を決めたときに、`evaluate --skills llm` を推薦と同じ検索文にすると高橋さんが選んだ。最初は 2 の形で書き、レビューの指摘で 1 にした)。

- `EvaluateSearch` は読み取りの元(`OccupationAnalyzer`)を受け取る。候補を作り、期待する科目名が候補にあるかを確かめてから、職業ごとに読み取り、読み取りで検索する。結果の検索文は読み取りの `query`
- `HandwrittenProfiles` は評価データの隣(`evaluate_search.py`)に移し、検索の評価、選び直しの評価、実験で同じものを使う。手書きの読み取りは、評価データの職業名をそのまま解釈にし、前提を持たない
- `EvaluationCase` は検索文を作らない
- `evaluate` の先頭に、評価データの職業名と手書きのスキルで測ったか、LLM の解釈とスキルで測ったかを出す。見出しと読み取りの元は、`--skills` の値から同じ表で引く

## 理由

- 検索文の作り方が推薦と 1 か所になるので、推薦の検索文が変わっても評価がずれない
- 選び直しの評価と実験がすでに読み取りの形で手書きのスキルを扱っているので、検索の評価もそれにそろえる
- DB の確かめを先にすれば、準備の誤りで読み取りの費用を無駄にしない

## 受け入れたトレードオフ

- 手書きの読み取りは `OccupationProfile` なので、評価データの手書きのスキルは 3〜6 個でないと作れない。評価データは試験で 3 個以上を確かめていて、今は 4〜5 個
- `evaluate --skills llm` の数字は、直す前(評価データの職業名 + LLM のスキル)と比べられない
- 読み取りは今までどおり 1 件ずつ呼ぶ。1 回の読み取りは揺れて再現率が数ポイント動く(ADR 0065)ので、指示文を比べるときは 1 回の `evaluate` では決めない

## 再検討する条件

- 推薦の検索文が読み取り以外の情報(前提など)を使うようになったとき
- 読み取りの指示文を比べる道具を作るとき(回数を重ねて交互に流す)
