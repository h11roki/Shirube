# 0027. バックエンドは HS256 の短い JWT で利用者を確かめ、users 表には Google の sub だけを持ち、他人の Plan は 404 にする

- ステータス: 承認
- 日付: 2026-10-16

## 文脈

ADR 0011 で、認証は Auth.js(Next.js)の Google ログインとし、Next.js の Route Handler からバックエンドへ短寿命の署名付き JWT で本人を渡し、バックエンドは署名を確かめて利用者を特定し、Plan の持ち主の確認(認可)を行うと決めた。そのとき JWT の検証鍵をフロントとバックエンドで共有することを受け入れた。

フェーズ 6 で `POST /api/v1/plans` と `GET /api/v1/plans/{id}` ができたが、認証が無く、誰でも道標を作れて OpenAI の費用がかかり、id を知れば誰の Plan でも読める(ADR 0026)。フェーズ 7 では、バックエンドの側(JWT の検証、利用者、持ち主の確認)を先に作り、フロントの Auth.js と Route Handler は次に作る。

## 検討した選択肢

JWT の署名

1. 共有鍵の HS256
2. 鍵ペアの EdDSA(フロントが秘密鍵で署名し、バックエンドは公開鍵で確かめるだけ)

利用者の持ち方

1. users 表に内部の id と Google の sub だけを持ち、plans は内部の id を持つ
2. users 表に sub、メール、名前を持つ
3. plans に sub を直接持つ

他人の Plan を読もうとしたとき

1. 404
2. 403

持ち主の無い今までの Plan(手元の試作だけ)

1. 移行で消す
2. 持ち主なしで残し、誰も読めないようにする

## 決定

高橋さんがどれも 1 を選んだ。

JWT

- Route Handler は、利用者ごとのリクエストのたびに HS256 の JWT を作り、`Authorization: Bearer` で渡す。鍵は環境変数 `AUTH_JWT_SECRET`(32 文字以上)で、フロントとバックエンドが同じ値を持つ
- 欄は `sub`(Google の sub)、`iss`(`shirube-frontend`)、`aud`(`shirube-backend`)、`iat`、`exp`。バックエンドはアルゴリズムを HS256 に限り、署名、`iss`、`aud`、`exp`、`iat` が先の時刻でないことを確かめ(時計のずれに 30 秒の余裕を持つ)、`iat` と `exp` が整数の秒でないもの、`exp - iat` が 5 分を超えるもの、`sub` が空のものも受け付けない
- 確かめる部品はポート(`TokenVerifier`)の後ろに置き、PyJWT で実装する(ADR 0011 の再検討の条件の Cognito に替えるとき差し替える)

利用者

- users 表は内部の id(UUID)、Google の sub(一意)、作った時刻だけを持つ。メールと名前は保存せず、画面は Auth.js のセッションから出す
- users 表の sub は提供元を前に付けて持つ(Google は `google:<sub>`)。ほかの提供元や CLI と名前が重ならない
- 確かめた JWT の sub で users 表を引き、無ければ作る(初めてのログインで作られる)。ふだんは読むだけで、初めてのときだけ書く
- plans は持ち主の内部の id を必須の列で持つ。Plan(domain)も持ち主の id を持つ
- CLI は Google のログインを持たないので、`plan create` は sub が `cli:local` の利用者として作る(JWT の利用者は必ず `google:` で始まるので、JWT からはこの利用者になれない)。`plan show` は持ち主を確かめない(サーバーの中で動かす管理用)

API

- `POST /api/v1/plans` と `GET /api/v1/plans/{id}` は JWT が要る。無い、または確かめられないときは 401 と `WWW-Authenticate: Bearer`。`/api/v1/health` は要らない
- `GET` は持ち主が本人でない Plan を、無い Plan と同じ 404 にする。持ち主の確認はユースケース(GetPlan)で行う

移行

- 0004 の移行で、今までの plans の行を消し、users 表と plans.user_id(必須、users を指す、索引つき)を足す

## 理由

- HS256 は 1 つの鍵を 2 つのコンテナに渡すだけで済み、ADR 0011 で受け入れた形のまま。同じ EC2 の中で完結し、JWT は 5 分で切れる
- メールや名前を持たなければ、漏れたときに守るべき個人情報がほとんど無い。Google の sub は Google の中での利用者の番号で、それだけでは個人を特定しにくい
- 内部の id を持てば、認証の提供元を Cognito などに替えても、Plan の持ち主を書き換えずに users 表の対応だけを直せばよい
- 404 にすると、他人の Plan の id が存在するかどうかも分からない
- 本番はまだ無く、持ち主の無い Plan は手元の試作だけなので、消せば「持ち主の無い Plan」の扱いを考えなくてよい

## 受け入れたトレードオフ

- バックエンドの `AUTH_JWT_SECRET` が漏れると、その鍵で誰の JWT でも作れる(ADR 0011)
- バックエンドから利用者に連絡できない(メールを持たない)。必要になったら、保存する情報とプライバシーポリシーを決めてから足す
- 401 か 404 かで、バックエンドに直接届く人には、JWT の有無による違いが見える。backend は手元と同じく外に公開せず、フロントの Route Handler からだけ呼ぶ(ADR 0008)
- 手元に保存した試作の道標は、移行で消える
- CLI で作った道標は、画面のどの利用者のものにもならない

## 再検討する条件

- バックエンドの鍵の漏れを心配する理由が増えたとき(鍵ペアに替える)
- 利用者への知らせなど、連絡先が要る機能を足すとき
- 認証の提供元を替えるとき(ADR 0011)
