# 0087. 本番で道標を作るごとに、費用と時間と失敗の種類を利用者の番号と入力を持たない形で残し、サーバーの CLI で日ごとに見る

- ステータス: 承認
- 日付: 2026-11-04

## 文脈

- 本番の OpenAI は前払いで、自動の補充を切っている(ADR 0038)。残高が尽きると、道標は「推薦に使う外部のサービスの呼び出しに失敗しました」で失敗する。ただ、それが残高切れなのか、時間切れや一時の混み合いなのかは、アプリのログにしか残らない。ログは 30MB で古いものから消える
- 1 件の費用と段ごとの時間は、実験(ADR 0048)では測っている。本番では数えていない
- 道標の表には、受け付けた日時、作り始めた日時、作り終えた日時と、画面に出す決まった失敗の文がある。ただ、道標を消すか退会すると消える
- OpenAI には残高を読む API が無い

## 検討した選択肢

記録の置き場

1. 道標とは別の表に、利用者の番号と入力を持たない形で残す
2. 道標の表に列を足す
3. アプリのログに 1 件 1 行で書くだけ

見方

1. サーバーで CLI の報告を流す
2. CLI に加えて、失敗が続いたときや 1 日の費用が上限を超えたときにメールで知らせる
3. 管理者だけが見られる Web の画面

残高

1. 報告には本番で使った額だけを出し、失敗の種類で残高切れを分けて見せる
2. 入れた額と日付を設定に書き、使った額を引いて残りの見込みも出す

## 決定

高橋さんが、どれも 1 を選んだ。

- 表 `plan_builds` に、道標を 1 件作り終えるごとに 1 行を残す。worker が作るときも、CLI の `plan create` で作るときも残す。残すのは次のもの
  - 作り終えた日時
  - 結果。成功、失敗、捨てた(作っている間に作成中でなくなり、結果を保存しなかった)、止まった(作成中のまま上限の時間を過ぎて失敗にした。ADR 0029)のどれか
  - 失敗の種類。例外の型の名前を、外側から原因へたどった順に並べたもの(`CourseSelectionError`、`RateLimitError` など)と、たどった例外を奥から見て最初に見つかった短い符号(OpenAI の `insufficient_quota` など)。原因は Python のトレースバックと同じに、`from` で付けた原因が無ければ、隠していない処理中の例外をたどる(8 段まで)。符号は英小文字、数字、`_` で 64 字までのものだけを残す
  - 待ちの秒(受け付けてから作り始めるまで)
  - 段ごとにかかった秒(読み取り、検索、選び直し、置く)
  - モデルごとのトークン(入力、そのうちキャッシュに当たった分、出力)
- 残さないもの
  - 利用者の番号、道標の番号、職業名などの入力
  - 例外の文。入力した職業名が入りうるため
- 円の額は残さない。トークンを残し、報告のときに料金表で円にする。料金が変わっても、料金表を直せば前の記録も直る。料金表は実験の CLI と共有する
- 検索文の埋め込みは数えない。LangChain の使用量の記録に入らず、1 件 0.01 円にも満たないため
- 止まった道標は、使ったトークンと段ごとの秒が分からない。結果と待ちの秒だけを残す
- 記録は消さない。利用者の番号を持たないので、道標を消しても退会しても残る。そのことをプライバシーポリシーの「保存する情報」と「消し方」に書く
- 段の名前やトークンの項目を変えるときは、記録の JSON もマイグレーションで直す。記録は消さないので、直さないと古い行を読めなくなる
- 記録を書けなかったときも、道標は失敗にしない。段を書けなかったときと同じに、ログに残して続ける。記録は道標を保存したあとに書き、トークンを読めなければトークン無しで書く
- `python -m app.presentation.cli.report`(`--days`、1〜3650、既定 14)で、日本時間の日ごとに次のものを出す。終わりに期間全体の合計とモデルごとの費用を出す
  - 件数(結果ごと)と、失敗の種類ごとの件数
  - 待ちと、作るのにかかった時間(どちらも中央値と最大)
  - 費用(合計と、トークンを数えた 1 回あたり。料金表に無いモデルがあれば 1 回あたりは出さない)
- 「捨てた」は、別のプロセスが止まったとして先に失敗にした道標を、元の worker があとで作り終えたときにだけ起きる。同じ道標が「止まった」でも 1 行あるので、捨てた行は道標の件数と待ちには数えず、費用と作る時間に入れて、別の行で回数を出す。失敗の原因は、失敗の行と捨てた行の両方から回数で数える(止まった行には原因が無いので、捨てた行で残高切れが分かる)
- 本番では `docker compose -f compose.prod.yaml exec backend` で報告を流す。符号が `insufficient_quota` の失敗は「残高切れ」と添えて出す。料金表に無いモデルがあれば、その分を費用に入れていないと出す
- 残高は報告に出さない。OpenAI の画面で見る

## 理由

- 別の表に分けて利用者の番号と入力を持たなければ、消した道標や退会した人の分も費用の数えから落ちない。道標を消したあとは、記録が誰のものかを辿れない
- 円の額ではなく、トークンという起きた事実を残す。料金の変更にも、モデルの入れ替えにも強い
- CLI なら、外に新しい入口を作らずに済む。ssh で入れる人だけが見られる
- 入れた額から引いた見込みは、手元の実験でも同じキーを使うので実際より多めに出る。間違った安心を与える数字は出さない

## 受け入れたトレードオフ

- 見に行かないと気付かない。残高切れは、利用者の道標が失敗して初めて記録に出る(画面の文は今と同じ)
- 報告の費用は本番の分だけで、手元の実験の分は入らないので、OpenAI の残高とは合わない
- 表は増え続ける。1 日 30 件が上限(ADR 0038)なので、多くても 1 年で 1 万行ほど
- 作り終えた日時や待ちの秒を道標の表と突き合わせれば、道標が残っている間は、どの道標の記録か分かる。道標を消せば分からなくなる。プライバシーポリシーにもそう書き、「誰のものか分からない」とは書かない。記録は費用と障害を知るためにだけ使う

## 再検討する条件

- 利用者が増え、残高切れや失敗の続きに気付くのが遅れて困ったとき(メールの知らせ)
- LLM の会社を替えるか、複数の会社を使うとき(料金表と符号の読み方)
