# 0065. 職業の読み取りに学科の分野を書く案は、測って採らない

- ステータス: 承認
- 日付: 2026-10-26

## 文脈

- ADR 0064 で 50 職業に増やして比べ直すと、選び直しに渡した候補の再現率は 85.8% で、期待する科目 151 のうちおよそ 1 割が候補に入らなかった
- 候補の取り方を手元で替えて測った(全体の上位 10 + 交互、RRF k=60、類似度の最大、類似度の和)。手書きのスキルではどれも今の交互と同じくらい(0.90〜0.92)で、50 職業の pair で記録した LLM のスキルでは今の交互が一番よかった(0.858。RRF は -6.9 ポイント、類似度の和は -4.7 ポイントで、どちらも職業ごとの並べ替え検定で p < 0.05)。取り方は替えない
- LLM のスキルで取りこぼした 25 件のうち 17 件は、手書きのスキルなら 20 位以内に入る。手書きと LLM の差(0.918 と 0.858)は、職業の読み取り(解釈とスキル)から来ている
- 50 職業の pair の 300 回の読み取りのうち 48 回が「ITエンジニア」だった。ADR 0032 が広く読むとした Web、スマホアプリ、クラウドのほかに、学科で学ぶ分野で決まる職種(AI・機械学習、自然言語処理、検索・推薦、ソフトウェア開発)と、役割の違う職業(テック系スタートアップの起業家、社内 SE、金融系システムエンジニア)まで「ITエンジニア」と読んだ。EV・蓄電池の制御エンジニアは「制御エンジニア」、光通信エンジニアは「通信エンジニア」と読み、分野の語を落とした。起業家を「ITエンジニア」と読んだ回は、アントレプレナーシップの授業(手書きのスキルでは 1 位)が候補から落ちた
- 指示文は「学科の授業に無い応用分野で決まる細かい職種だけ広く読む」と決めているが、LLM は学科にどの分野の授業があるかを知らないまま判断している。ADR 0032 の再検討する条件(具体的な職業名まで広く読まれ、期待する授業が上位 20 件から漏れたとき)にあたる
- 測るには、`evaluate --skills llm` が推薦と同じ検索文(解釈した職業名とスキル)で測る必要がある。今は評価データの職業名と LLM のスキルで検索文を作り、解釈が替わる効き目を測れないので、先に ADR 0066 で直す

## 検討した選択肢

1. 学科の分野を指示文に書く。候補の 188 科目の名前から学科の分野をまとめて指示文に書き、広く読むのはそこに無い分野や道具で決まる職種だけにする。広く読むときも仕事の役割(起業家、研究者、教員、営業など)は残し、学科の分野にある分野の語はスキルに入れる。読み取りのポートは変えず、入力は 300 トークンほど増える
2. 広く読む決まりだけ締める。分野の一覧は書かず、学科で学ぶ分野の職種は広く読まない、役割と分野の語は残す、とだけ書く。変更は小さいが、LLM は学科の授業を知らないまま判断する
3. 学科の科目名の一覧を渡す。188 科目の名前を指示文に渡し、スキルを授業の言葉に寄せる。読み取りのポートが学科を受け取る形に変わり、入力はおよそ 4 倍になる。スキルが科目名の写しになり、画面で見せるスキルとして不自然になりうる

## 決定

高橋さんが 1 を選んで試し、測った結果を見て、指示文を前の文面に戻すことを選んだ。

### 試した指示文

- 候補の 188 科目の名前から、学科の分野を 18 行にまとめて指示文に置いた(電気回路と電子回路、半導体、高周波と通信、信号処理とメディア情報処理、制御と組み込み、論理回路とアーキテクチャ、プログラミングとアルゴリズム、OS とネットワーク、ソフトウェア工学、データサイエンスと AI、数学、物理と化学、エネルギーの活用と状態推定、情報社会と倫理、教職、経営と起業、課題解決の実践とキャリア、計算言語学)。評価データの判定や取りこぼしからは足さなかった
- 職業名で仕事を決めている分野が一覧のどれに当たるかを、解釈より先に答えさせ(構造化出力の欄 `department_field`)、当たるときと迷うときは職業名をそのまま書き、当たらず道具や製品で決まる細かい職種のときだけ広く読む。広く読むときも役割を残し、分野の名前を職業名にしない。スキルには、職業名の分野と役割の中心になる知識のうち一覧にあるものを入れ、役割に関わらない分野は数合わせに入れない
- 新しい決まりの例には評価データの職業を使わなかった
- 途中の文面は 2 つあった。1 つ目(一覧と決まりだけ)は、50 職業を 1 回読ませると、解釈に分野の名前を写し(半導体・LSI 設計エンジニアが「半導体工学・集積デバイス」、起業家が「経営と起業」)、システムエンジニアや IoT エンジニアまで新たに「ITエンジニア」と読んだので、2 回目の途中で止めた。2 つ目(解釈とスキルの決まりを足す)は、10 職業を 1 回ずつ読ませると、システムエンジニア、画像・音声処理エンジニア、自然言語処理エンジニアをまだ「ITエンジニア」と読んだ。分野を先に答えさせる形にして、同じ 10 職業では Web とフロントエンドだけを広く読むようになったので、これを測った

### 測り方(変える前に決めた)

前と後の読み取りの実装を、50 職業ごとに交互に(先に流す側を職業と回で入れ替えて)3 回ずつ動かし、推薦と同じ取り方(3-large、スキルごと)で検索して、職業ごとの @20 の再現率(選び直しに渡す候補の再現率と同じ)を 3 回で平均した。差ありは職業ごとに前と後を入れ替える並べ替え検定(10,000 通り、両側、p < 0.05)で決める。ねらいの指標は @20 の再現率で、@10 の再現率と「ITエンジニア」と読んだ数はほかの指標として見る。評価データに無いフロントエンドエンジニアも 3 回ずつ読ませた。

### 結果

| 指標 | 前 | 後 | 差(並べ替え検定) |
|---|---|---|---|
| @20 の再現率(ねらい、50 職業) | 0.910 | 0.865 | -4.4 ポイント(上がった 3、下がった 13、p = 0.105) |
| @20 の再現率(初めの 30 職業) | 0.955 | 0.884 | -7.1 ポイント(p = 0.008) |
| @20 の再現率(足した 20 職業) | 0.843 | 0.838 | -0.5 ポイント(p = 0.969) |
| @10 の再現率(50 職業) | 0.773 | 0.768 | -0.4 ポイント(p = 0.868) |
| 「ITエンジニア」と読んだ回(153 回のうち) | 35 | 8 | |
| 前提を書いた回(153 回のうち) | 99 | 122 | |

- 前の @20 の再現率(0.910)は、文脈に書いた同じ指示文の値(0.858)より高い。どちらも選び直しに渡す候補の再現率と同じ物差しだが、0.858 は 50 職業の pair の読み取り 1 回(後の側の 1 回目)で、0.910 は別に読ませた 3 回の平均。同じ指示文でも読み取りは回ごとに揺れて再現率が数ポイント動くので、前と後を同じ時間に交互に読ませて比べた
- 広く読みすぎることは直った。後で「ITエンジニア」と読んだのは Web エンジニア(3 回)、フロントエンドエンジニア(3 回)、スマートフォンアプリ開発エンジニア(2 回)だけ。ただしクラウドエンジニアは 3 回ともそのまま読み、ADR 0032 の決まりから外れた
- 解釈の直しは効いた。テック系スタートアップの起業家は「ITエンジニア」から「テック系スタートアップの起業家」と読むようになり、再現率が 0.00 から 0.56 になった(アントレプレナーシップとコーオプ演習が入った)。計算機科学の研究者はスキルに OS と並列処理が入り、0.38 から 0.71 になった
- スキルが足を引っ張った。下がった 13 職業の多くで、スキルに一覧の言葉(情報社会と倫理、経営と起業、技術者倫理、電気回路)を写し、その職業に固有のスキル(IT コンサルタントの業務分析、フィールドエンジニアのトラブルシュート、プロダクトマネージャーのプロジェクト管理)が押し出された。IT コンサルタントは現代の経営とコーオプ演習、フィールドエンジニアはコンピュータネットワーク、EV・蓄電池の制御エンジニアは組み込みシステムとシステム設計 CAD が候補から落ちた
- 費用は試しも含めて読み取り約 460 回、約 80 円だった

### 戻す判断

ねらいの @20 の再現率は上がらず、初めの 30 職業では差ありで下がった。スキルの決まりだけを外して測り直す案もあったが、同じ 50 職業の取りこぼしを見て指示文を 3 度目に直すと、その職業に合わせただけの結果になりやすい(ADR 0064 で、取りこぼしを見て決めた ADR 0063 の差が、見ていない職業では出なかった)。高橋さんは前の文面に戻すことを選んだ。試した文面はコミットの履歴に残す。

## 理由

- 前もって決めた指標で改善が出なかった変更は入れない。広く読みすぎることが直っても、候補の再現率が下がれば推薦は悪くなる
- 指示文を同じ 50 職業で繰り返し直すほど、評価データに合わせた指示文になる。次に読み取りを直すときは、評価データに新しい職業を足して、決まりを決めたあとに見る職業で確かめる

## 受け入れたトレードオフ

- 広く読みすぎることは残る(50 職業の読み取りの 2 割ほどが「ITエンジニア」)。起業家を「ITエンジニア」と読む回は、アントレプレナーシップの授業が候補に入らない
- 試しに約 80 円かかった
- 測った道具(前と後の読み取りの実装を同じプロセスで交互に動かす)は、前の実装をファイルから読み込む使い捨てのもので、リポジトリに置いていない。`experiment pair` は指示文を切り替えられない。手順はこの ADR に書いた。読み取りの直しをまた測るときは、繰り返せる道具にする

## 再検討する条件

- 評価データに、まだ見ていない職業を足したとき(読み取りの直しを、決まりを決めたあとに見る職業で確かめられる)
- 解釈とスキルを別々に作る形(読み取りを 2 段にする、またはスキルの生成に分野の一覧を見せない)を試すとき
- 広く読みすぎることへの利用者の声が出たとき
- 学科を広げるとき
