# 0065. 職業の読み取りの指示文に学科の分野を書き、広く読むのはそこに無い分野の職種だけにする

- ステータス: 承認
- 日付: 2026-10-26

## 文脈

- ADR 0064 で 50 職業に増やして比べ直すと、選び直しに渡した候補の再現率は 85.8% で、期待する科目 151 のうちおよそ 1 割が候補に入らなかった
- 候補の取り方を手元で替えて測った(全体の上位 10 + 交互、RRF k=60、類似度の最大、類似度の和)。手書きのスキルではどれも今の交互と同じくらい(0.90〜0.92)で、50 職業の pair で記録した LLM のスキルでは今の交互が一番よかった(0.858。RRF は -6.9 ポイント、類似度の和は -4.7 ポイントで、どちらも職業ごとの並べ替え検定で p < 0.05)。取り方は替えない
- LLM のスキルで取りこぼした 25 件のうち 17 件は、手書きのスキルなら 20 位以内に入る。手書きと LLM の差(0.918 と 0.858)は、職業の読み取り(解釈とスキル)から来ている
- 50 職業の pair の 300 回の読み取りのうち 48 回が「ITエンジニア」だった。ADR 0032 が広く読むとした Web、スマホアプリ、クラウドのほかに、学科で学ぶ分野で決まる職種(AI・機械学習、自然言語処理、検索・推薦、ソフトウェア開発)と、役割の違う職業(テック系スタートアップの起業家、社内 SE、金融系システムエンジニア)まで「ITエンジニア」と読んだ。EV・蓄電池の制御エンジニアは「制御エンジニア」、光通信エンジニアは「通信エンジニア」と読み、分野の語を落とした。起業家を「ITエンジニア」と読んだ回は、アントレプレナーシップの授業(手書きのスキルでは 1 位)が候補から落ちた
- 指示文は「学科の授業に無い応用分野で決まる細かい職種だけ広く読む」と決めているが、LLM は学科にどの分野の授業があるかを知らないまま判断している。ADR 0032 の再検討する条件(具体的な職業名まで広く読まれ、期待する授業が上位 20 件から漏れたとき)にあたる
- `evaluate --skills llm` は、LLM の出したスキルを評価データの職業名と組み合わせて検索文を作る(ADR 0018)。本番は解釈した職業名とスキルで検索文を作る(ADR 0032)ので、解釈が替わる効き目を測れない(ADR 0032 にも書いた)

## 検討した選択肢

1. 学科の分野を指示文に書く。候補の 188 科目の名前から学科の分野を 17 ほどにまとめて指示文に書き、広く読むのはそこに無い分野や道具で決まる職種だけにする。広く読むときも仕事の役割(起業家、研究者、教員、営業など)は残し、学科の分野にある分野の語はスキルに入れる。読み取りのポートは変えず、入力は 300 トークンほど増える
2. 広く読む決まりだけ締める。分野の一覧は書かず、学科で学ぶ分野の職種は広く読まない、役割と分野の語は残す、とだけ書く。変更は小さいが、LLM は学科の授業を知らないまま判断する
3. 学科の科目名の一覧を渡す。188 科目の名前を指示文に渡し、スキルを授業の言葉に寄せる。読み取りのポートが学科を受け取る形に変わり、入力はおよそ 4 倍になる。スキルが科目名の写しになり、画面で見せるスキルとして不自然になりうる

## 決定

高橋さんが 1 を選んだ。

- 学科の分野は、候補の 188 科目の名前からまとめる(評価データの判定や取りこぼしからは足さない)。電子情報工学科の分野として指示文に置く。今の指示文もすでに電子情報工学科を決め打ちしている(ADR 0032)
- 解釈: 職業名の分野が学科の分野にあれば、そのまま解釈する。学科の分野に無い応用分野や、授業で扱わない道具や製品で決まる細かい職種のときだけ広く読む。広く読むときも仕事の役割は残す。Webエンジニアを「ITエンジニア」と読む例は残す
- スキル: 職業名に含まれる分野のうち学科の分野にあるものはスキルに入れる。仕事の役割に要る知識(経営、教育など)も、学科の分野にあればスキルに入れてよい
- 新しい決まりの例には、評価データの職業を使わない。評価データの 50 職業の取りこぼしを見て決まりを決めたので、同じ 50 職業で測った差はよく出うる(ADR 0064 で、取りこぼしを見て決めた ADR 0063 の差が、見ていない職業では出なかった)。新しい職業での確かめは、評価データに職業を足すときに行う
- `evaluate --skills llm` は、本番と同じく解釈した職業名とスキルで検索文を作るように直す。手書きのスキルは今までどおり評価データの職業名で作る
- 測り方は変える前に決める。前と後の指示文を、50 職業ごとに交互に(先に流す側を職業と回で入れ替えて)3 回ずつ読ませ、本番と同じ取り方で検索して、職業ごとの @20 の再現率(選び直しに渡す候補の再現率と同じ)を 3 回で平均する。差ありは、職業ごとに前と後を入れ替える並べ替え検定(10,000 通り、両側、p < 0.05)で決める。ねらいの指標は @20 の再現率で、@10 の再現率と「ITエンジニア」と読んだ数はほかの指標として見る。ADR 0032 の細かい職種(評価データの Web エンジニア、スマートフォンアプリ開発エンジニア、クラウドエンジニアと、評価データに無いフロントエンドエンジニア)を前と同じく広く読むかも見る(フロントエンドエンジニアは前と後で 3 回ずつ読ませる)。費用は読み取り 300 回で約 45 円
- 選び直しまで通した比べ(pair、約 280 円)は、OpenAI の残高を補充してから行う

## 理由

- 取りこぼしの原因は読み取りで、LLM が学科の分野を知らないことが根本にある。分野を書けば、広く読むかを当て推量でなく決めた一覧で判断できる
- 分野は科目名からまとめるので、評価データの答えを指示文に持ち込まない。一覧は 300 トークンほどで、読み取りの費用はほとんど増えない(1 回約 0.15 円が 0.2 円ほど)
- 読み取りのポートを変えずに済む。他の学科へ広げるときに、一覧を学科ごとに持つ形へ移せばよい
- 読み取りだけなら選び直し(nano)を通さずに測れるので、残高の少ない今でも 50 職業 × 3 回で比べられる

## 受け入れたトレードオフ

- 分野の一覧は電子情報工学科の決め打ちになる。学科を広げるときは、一覧を学科ごとに持って読み取りに渡す形に変える
- 一覧のまとめ方(どの科目をどの分野にまとめるか)に Claude の見方が入る。科目名から機械的に言える範囲にとどめる
- 同じ 50 職業で決まりを決めて測るので、差はよく出うる。見ていない職業で確かめるまで、改善の大きさは割り引いて読む
- 検索の再現率は上がっても、選び直しの関係なしや中心の適合率がどう動くかは、pair を流すまで分からない
- `evaluate --skills llm` の数字は、直す前(職業名 + LLM のスキル)と比べられなくなる

## 再検討する条件

- @20 の再現率が差ありにならないとき、または学科の分野で決まる職種(AI・機械学習エンジニアなど)をまだ「ITエンジニア」と読むとき
- ADR 0032 の細かい職種まで広く読まれなくなったとき
- 選び直しまで通した pair で、選んだ科目のうち関係なしや中心の適合率が悪くなったとき
- 学科を広げるとき
