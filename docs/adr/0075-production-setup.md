# 0075. 本番は DuckDNS のサブドメインと Caddy で公開し、手元の DB の科目データを移し、サーバーでビルドする

- ステータス: 承認(地域はシドニー。0076)
- 日付: 2026-10-30

## 文脈

- ADR 0009 で、本番は EC2 1 台で docker compose を動かすと決めた。今の `compose.yaml` は開発用で(自動の読み直し、ソースのマウント、`pnpm dev`、DB のパスワードの決め打ち、DB のポートの公開)、本番用の compose、frontend の本番のビルド、TLS を受けるプロキシ、バックアップ、手順書が無い
- 本番化に先送りしていたことがある。HSTS とプロキシ(ADR 0045)、プロキシでの本文の大きさの制限(ADR 0039)、ログの回転(ADR 0042)、OpenAI の前払い(ADR 0038)、本番の DB への科目データ(ADR 0040)
- 高橋さんは就活のポートフォリオとして公開したく、費用は抑えたい。費用はドメイン(.com で年 1,700 円前後)よりサーバー(t4g.small で月 2,500〜2,800 円)が大きい。2025-07-15 以降の新しい AWS アカウントには、6 か月のクレジット($100、条件で最大 +$100)がある
- 本番のイメージは取り込みの依存(Playwright など)を入れないので、本番では時間割表とシラバスを取り込めない

## 検討した選択肢

- ドメイン: 独自の .com を買う / 無料のサブドメイン(DuckDNS)
- TLS: Caddy / nginx と certbot
- 科目データ: 手元の DB から移す / 本番で取り込み直す
- ビルド: サーバーで作る / CI で作って配る
- サーバー: 新しい AWS アカウントのクレジットを使う / 今あるアカウント / ほかの安いサーバー

## 決定

高橋さんが、DuckDNS、Caddy、手元の DB から移す、サーバーで作る、新しいアカウントのクレジットを使う、を選んだ。

- 本番は `compose.prod.yaml` で動かし、開発用の `compose.yaml` はそのまま残す。秘密の値と設定はサーバーのリポジトリ直下の `.env`(git の管理外、ひな形は `.env.example`)から compose が読む
  - db: パスワードは `POSTGRES_PASSWORD`。ポートは外に出さない
  - backend と worker: backend が作ったイメージ(shirube-prod-backend)を worker も使う。自動の読み直しもマウントもしない。backend のポートも外に出さず、frontend からだけ呼ぶ。推薦の設定(埋め込みのモデル、検索の取り方、選び直しの票の数など)は `.env` に書けば渡り、書かなければ既定で動く
  - frontend: Dockerfile の `build` の段で、`SITE_URL`(`https://` と `SITE_DOMAIN`)を渡して `next build` し、開発用の依存を外す。`runner` の段に動かすのに要るもの(`next.config.ts` が読む `src` を含む。ビルドのキャッシュは捨てる)だけを写し、`next start` を node の利用者で動かす。応答の圧縮は Next が行う。開発用の compose は `dev` の段を使う
  - caddy: 80 と 443 を受け、Let's Encrypt の証明書を自動で取って更新し、frontend に渡す。HSTS(1 年)を付け、本文を 1MB までにし、アクセスログを出す。ログは要求と応答のヘッダー、TLS の中身、ログインの戻り先の URL の認証の符号を消し、プライバシーポリシーに書いた IP、時刻、要求の方法と URL、状態コード、応答の大きさと時間に絞る
  - どのサービスも `restart: unless-stopped`。ログは json-file で 1 つのサービスにつき 10MB × 3 まで残し、古いものから消す。backend は uvicorn のアクセスログを書かない(URL は Caddy のログにだけ残し、ポリシーに書いた項目に絞る)
- マイグレーションは、デプロイの手順で `alembic upgrade head` を手で流す。更新では先にイメージを作り、backend と worker を止めてから流して入れ替える
- 科目データは、手元の DB を本番と同じスキーマにし、今のモデル以外の埋め込みを消してから、科目の表(`course_sections`、`syllabi`、`syllabus_codes`、`syllabus_chunks`、`embeddings`)の中身だけを `pg_dump` で出し、本番でスキーマを作ってから戻す。利用者と道標の表は移さない。入れ替えるときは backend と worker を止める
- バックアップは、サーバーの cron で毎日 `backup.sh` を流して DB 全体を `pg_dump` し、新しい 7 つをサーバーに残す(日数で比べると、前の回より速く終わった日に 8 日目が残るため)。7 日より古いものは毎回初めに消す(失敗が続いたときやサーバーを止めていたときも 7 日を超えて残さない)。本人だけが読める権限で作り、同時には 1 つしか流さない。サーバーの時刻は日本時間にする。失敗すると途中のファイルを本物にせず、ログに理由を残す。戻すときは backend と worker を止め、1 つのトランザクションで戻す
- 退会した人の情報もバックアップに最長 7 日残ることを、高橋さんの判断でプライバシーポリシーに書き足す(改定の日付を出す)。ログの量(部品ごとに 30MB)もポリシーに書く(ADR 0042 で本番化のときに書き足すとしていた)
- サーバーは t4g.small(Arm、メモリ 2GB)に 2GB のスワップを足し、Elastic IP を付けて DuckDNS の向き先を固定する。AWS の予算の通知を付ける
- 手順は README の「本番」に書く
- CI の production の job で、本番の構成を試しの値(SITE_DOMAIN は localhost で、Caddy が内部の証明書を出す)で組み立てて起動し、HTTPS のトップ、HSTS、ログインなしの API の 401、HTTP からの転送、backup.sh を確かめる。イメージをサーバーで初めて作るので、壊れたらデプロイの前に分かるようにする

## 理由

- 無料のサブドメインでも、HTTPS でポートフォリオに載せられ、ログイン前のトップで見本の道標を見せられる。独自のドメインには、SITE_URL、DNS、Google のリダイレクト URI を替えてビルドし直せば移れる
- Caddy は証明書の取得と更新が組み込みで、設定が数行で済む
- 手元の DB を移せば、埋め込みに費用がかからず、本番のイメージに取り込みの依存を入れずに済み、評価と同じデータになる
- サーバーで作れば部品が少なく、初めてのデプロイに向く
- 開発用の compose を残せば、手元の開発の手順は変わらない

## 受け入れたトレードオフ

- クレジットが切れたあとは月 2,500 円ほどかかる。続けるかはそのときに決める
- バックアップはサーバーの中だけなので、ディスクやサーバーごと失うと消える。消えて困る利用者のデータが増えたら、外に送る
- バックアップから戻すと、そのあとに消した道標や退会した人の情報が戻る。消した記録を残していないので戻したあとに消し直せず、ポリシーで、戻したことを知らせ、もう一度消すか退会するよう頼むと約束する
- DuckDNS は無料のサービスで、止まると名前が引けなくなる
- Google ログインを誰でも使えるようにできるかは、同意画面を公開するときに Google の条件で確かめる。できなければテストの利用者(100 人まで)だけがログインでき、ほかの人はトップの見本だけを見る
- 小さいサーバーでは `next build` にメモリが足りないことがあり、スワップで補う
- マイグレーションを手で流すので、流し忘れると新しい版が古いスキーマで動く。手順に書いて防ぐ
- コンテナを root 以外で動かすのは frontend だけ。backend は開発用の compose とイメージを共有するので、今は変えない

## 再検討する条件

- クレジットが切れるとき(続けるか、止めるか、安いサーバーに移るか)
- 独自のドメインを買うとき
- 利用者が増え、停止やバックアップの喪失が許されなくなったとき(ADR 0009 の再検討する条件)
- デプロイを繰り返すようになり、CI で作って配るほうが楽になったとき
