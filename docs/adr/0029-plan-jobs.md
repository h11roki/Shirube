# 0029. 道標は DB をキューにした worker が非同期に作り、API は状態を持つ Plan を 202 で受け付けてポーリングで返す

- ステータス: 承認(止まったとみなす時間と止める猶予は 0037 で 20 分と 16 分に延ばした。始める学期の既定は 0078 で春学期にした)
- 日付: 2026-10-19

## 文脈

ADR 0024 で、道標(Plan)は `POST /api/v1/plans` の中で同期に作って保存し、status は持たないと決めた。ADR 0026 で、その API の組み立て方、本文、エラーの返し方を決め、POST は 201 と道標を返すとした。生成は OpenAI を 3 回呼び(職業のスキル、検索の埋め込み、科目の選び)、ふだん 10〜30 秒かかる。

ADR 0028 で、フロントの Route Handler の待ち(290 秒)を、バックエンドで全ての試行がタイムアウトしたときの所要時間(270 秒)より長くした。それでも OpenAI の SDK が守る `Retry-After`(120 秒まで)の待ちや、接続と読み込みのそれぞれに掛かるタイムアウトが重なると、フロントが 504 を返したあとに道標が保存されうる。利用者が作り直すと重複と二重の課金になる。0028 は、本命の解決を道標の作成の非同期化とした。

フェーズ 8 で、入力画面、結果画面、自分の道標の一覧を作る。結果画面は、作成中の道標も見せる必要がある。

## 検討した選択肢

仕事を動かす場所

1. DB をキューにした別プロセスの worker(compose に足す)
2. API のプロセスの中で、FastAPI の BackgroundTasks で動かす
3. Redis と専用のキュー(arq や RQ)

API の形

1. 道標に状態を持たせる。POST は 202 を返し、GET が状態と、完了なら中身を返す
2. 仕事を別の資源にする(`/plan-jobs`)。完了したら道標の id を返す

完了の知らせ方

1. 結果画面が GET を繰り返す(ポーリング)
2. Server-Sent Events で押し出す

失敗と取りっぱなし

1. 自動で再試行しない。失敗は決まった文で残し、利用者が作り直す。止まった仕事は時間で失敗にする
2. 決まった回数まで自動で再試行する

## 決定

高橋さんがどれも 1 を選んだ。同期で作ること、status を持たないこと、POST が 201 と道標を返すことは ADR 0024 と 0026 の決定を変えるので、両方のほかの決定をここに書き写して引き継ぎ、0024 と 0026 を置き換える。

組み立て(ADR 0026 から引き継ぐ)

- `presentation/api/app.py` の `create_app` が、組み立て済みのユースケースを受け取り、ルータとエラーの対応を持つ FastAPI を返す。ルータは受け取ったユースケースだけを使い、infrastructure を import しない。テストはフェイクを渡す
- `main.py`、`presentation/cli/`、`presentation/worker.py` が合成ルートで、共有する組み立ての部品と日本時間の今日は `presentation/composition.py` に置く
- 起動時に `OPENAI_API_KEY` が無ければ止める。`compose.yaml` は手元の環境変数を backend と worker に渡し、backend のポートは手元(127.0.0.1)だけに開ける
- OpenAI の呼び出しの失敗は、埋め込み・職業の解釈・選び直しのアダプタがポートのエラー(`EmbeddingError`、`OccupationAnalysisError`、`CourseSelectionError`)に包む。API も CLI も worker も OpenAI のライブラリの例外を知らない
- OpenAI の呼び出しには `OPENAI_TIMEOUT_SECONDS`(初期値 45 秒、ADR 0028)のタイムアウトと `OPENAI_MAX_RETRIES`(初期値 1 回)の再試行を付ける
- 年度は `CURRICULUM_YEAR` だけで決める。CLI の `--year` も省けばこの値を使う

エンドポイント(ADR 0026 から引き継ぎ、受け付けを変える)

- REST + OpenAPI 型生成。ブラウザ → Next.js Route Handler → FastAPI の順に呼ぶ。接頭辞は `/api/v1`。FastAPI の OpenAPI から openapi-typescript でフロントの型を生成する
- `POST /api/v1/plans`: 本文は職業名(前後の空白を除いて空でない 1 行、100 字まで)、回生(1〜4)、始める学期(`spring` / `autumn`、省けば今日から)、学科(省けない)、学科で分かれたクラスの選択(科目名 → クラス記号、50 科目まで、省けば空)。知らない欄は受け付けない。入力をその場で確かめてから、道標を「待ち」で保存し、202 と `Location: /api/v1/plans/{id}` と道標を返す。その場で確かめるのは、リクエストの形と、学科で分かれたクラスの選択(ADR 0025)と、残りの学期に検索の候補があること。どれも LLM を呼ぶ前に分かる
- `GET /api/v1/plans/{id}`: 自分の道標を返す
- 返す道標は、id、状態、作った条件を持ち、完了なら職業の解釈とスキル、学期ごとの置いた科目(科目名、中心か土台か、理由、前提にする中心、シラバスの主コード、授業コード、クラス記号、コマ、単位、クラスが確定しているか)と続きの授業、学期の単位、置けなかった科目、中心につながらず外した土台を持ち、失敗なら決まった文を持つ。画面の週の時間割は、コマからフロントが並べる
- フロントの結果画面は、完了か失敗になるまで 2 秒ごとに GET を呼ぶ(フェーズ 8)

エラー(ADR 0026 から引き継ぎ、生成の失敗は道標の状態に移す)

- 利用者が直せる誤りは 422 で、文に直し方が分かる中身を入れる。リクエストの形の誤り(「リクエストを確かめてください: 欄: 理由」の 1 文にまとめる。本文そのものの誤りは欄を「本文」とし、理由は pydantic の英語のまま。回生は型を変換せず整数だけを受け付ける)、選べないクラス(`ClassChoiceError`)、残りの学期に候補の無いとき(`NoCandidatesError`)
- 無い道標と他人の道標: 404(ADR 0027)
- サーバー側の問題(その年度の時間割が無い・埋め込まれていない、保存した道標を読めない、DB の接続など): 500 で「サーバーで道標を扱えませんでした」。例外の中身は文に入れず、投げ直した例外として uvicorn のログに残す
- API は生成しないので、埋め込みや LLM の失敗の 502 は無くなる。生成の失敗は道標の状態と決まった文で返す(下の「道標と状態」)
- どれも `{"detail": 文}`

道標と状態

- 道標は、id、持ち主、作った条件、状態を持ち、完了したときだけ結果(推薦と道標)を、失敗したときだけ決まった文を持つ。作った条件は、入力した職業名、学科、時間割とシラバスの年度、始める学期(回生と学期)、学科で分かれたクラスの選択、1 学期の単位の上限
- 状態は 待ち(pending)→ 作成中(running)→ 完了(succeeded)か失敗(failed)の順にだけ進む
- 失敗の文は決まった文にし、中身は worker のログに出す。埋め込みや LLM の呼び出しの失敗と、LLM の答えを使えないときは「推薦に使う外部のサービスの呼び出しに失敗しました」、止まった仕事は「道標を作る途中で止まりました」、それ以外は「サーバーで道標を扱えませんでした」
- 自動では再試行しない。利用者が作り直す
- id は UUID(v4)で、アプリが作る。結果は、始める学期から 4 回生の秋学期までを残りの学期とし、そのどれかに開講される科目を候補に推薦し(ADR 0025)、その年度の時間割で残りの学期に置いたもの。1 学期の単位の上限は `SEMESTER_CREDIT_LIMIT`(初期値 16)
- 今の学期は月で決める。4〜8 月は春学期、9〜3 月は秋学期。日付から学期を決める関数を domain に置き、API と CLI が今日の日付から既定値を出す。利用者は変えられる
- 道標は、状態が完了か失敗になったあとは変えない

worker

- `python -m app.presentation.worker` を合成ルートにし、compose に backend と同じイメージの worker を足す。1 つのプロセスが 1 件ずつ作る
- 繰り返し次のことをする。作成中のまま `PLAN_STALL_MINUTES`(初期値 15)分を過ぎた道標を失敗にする。一番古い待ちの道標を `SELECT ... FOR UPDATE SKIP LOCKED` で取り、同じトランザクションで作成中にして取った時刻を書く。結果を作って完了にするか、失敗にする。待ちが無ければ `WORKER_POLL_SECONDS`(初期値 1)秒待つ
- 時刻の比べ方は DB の時計にそろえる
- 15 分は、1 件の最悪の所要時間(3 回の呼び出し × (2 回の試行 × 45 秒 + `Retry-After` の 120 秒) ≒ 10.5 分)より長くとった
- 止める合図(SIGTERM)を受けたら新しい道標を取らず、作っている 1 件を終えてから止まる

CLI

- `plan create` は道標を待ちで保存し、worker を待たずに、その道標をその場で取って作る。`plan show` は状態も出す

保存

- plans 表に 1 つの道標を 1 行で保存する。列は id、持ち主、状態、作った条件(JSONB)、結果(JSONB、完了するまで空)、失敗の文、取った時刻、終えた時刻、作った時刻
- 結果は版番号を持つ JSON で、infrastructure に手で書いた変換で domain と行き来する。版を上げずに JSON の形を変えない。知らない版は読まずに止め、読むときは値の型まで確かめる。作った条件は結果から外して別の列にするので、結果の版を 2 にし、移行で版 1 の行を直す
- 作った条件は版番号を持たない。欄が 6 つと少なく、入力の形に直接つながるので、形を変えるときは移行で全ての行を直す。読むときは結果と同じく値の型まで確かめ、読めなければ道標を読めない誤りにする
- 版 2 の結果と作った条件をテストの固定ファイルに置き、変換がその形を作ることと、その形から同じ道標を読み戻せることを確かめる
- 置いたクラスは時間割の行を写して結果に持ち、時間割を入れ替えても作った道標は変わらない。推薦の科目と、秋学期に続く通年の授業は科目名で指し、読むときに引き直す

ADR 0028 の待ち時間

- 生成が HTTP の外に出るので、0028 の待ち時間の取り決め(フロントの待ち 290 秒、`OPENAI_TIMEOUT_SECONDS` の初期値 45 秒)は守る必要がなくなる。値はどちらも害が無いので変えない

## 理由

- DB をキューにすれば、API は仕事を抱えずステートレスのまま(ADR 0009)で、再起動や deploy でも待ちの仕事は消えない。Postgres はもうあるので、Redis のような新しい基盤も費用も要らない。`SKIP LOCKED` なら worker を増やしても同じ仕事を 2 つが取らない
- 道標に状態を持たせれば、道と Route Handler は今の 2 つのままで、フェーズ 8 の一覧に作成中の道標も並べられる
- ポーリングは今の Route Handler の転送のまま動く。1 件 10〜30 秒の生成なら 5〜15 回の問い合わせで、1 回は DB の 1 行を引くだけ
- 再試行しなければ、途中まで進んだ LLM の呼び出しが二重に課金されない。費用を抑えることを優先する
- 入力の誤りを POST で確かめれば、利用者はすぐ直せて、誤った入力で worker と LLM を使わない
- ADR 0024 から: Plan は作った時点の結果で、丸ごと読み書きできれば足りる。UUID は推測できない。手で書いた変換なら domain の名前を変えても保存の形は変わらず、版番号があれば古い道標を読めなくする変更に気づける。秋学期の履修登録がある 9 月からは秋学期を計画したい利用者が多い
- ADR 0026 から: create_app に渡せば、ルータはユースケースの型だけに依存し、テストはフェイクを渡すだけで済む。エラーを `detail` と状態コードにそろえれば、フロントの扱いが 1 つで済む。学期の既定値をサーバーが決めれば、業務の決まりがフロントに漏れない

## 受け入れたトレードオフ

- プロセスが 1 つ増え、compose と本番で worker も動かす
- 待ちの道標を取りに行く間隔の分(最大 1 秒)だけ、作り始めが遅れる。待ちが無くても 1 秒ごとに DB に問い合わせる
- OpenAI が一時的に失敗しただけでも、利用者が作り直す
- worker が止まったり、止める合図のあとに猶予を過ぎて殺されたりすると、作成中の道標は 15 分たってから失敗になる
- 道標の型が、結果のあるときと無いときに分かれる
- 候補の確かめは POST と worker で 2 回する
- API は生成しないが、検索の部品を組み立てるので、起動に `OPENAI_API_KEY` が要るまま
- ADR 0024 から: 科目ごとの集計を SQL でしにくい。変換のコードが増える。UUID は URL が長い。2〜3 月は授業の終わった秋学期が既定になる。置いたクラスを写すので、時間割の誤りを直しても作った道標には反映されない
- ADR 0026 から: 5xx と失敗の文は決まった文なので、利用者には原因が分からない。原因はサーバーのログで見る。取り込みの途中でシラバスが一部しか無いと、正しい入力でも候補が無い 422 になりうる

## 再検討する条件

- 同時に作る道標が増えて、1 つの worker で待ちが長くなったとき(worker を増やす)
- 進み具合(スキルを出した、科目を選んでいる)を画面に見せたくなったとき
- OpenAI の一時的な失敗で作り直す利用者が目立ったとき(再試行を足す)
- フロントがエラーの種類で分岐したくなったとき(エラーの種類を表す欄を足すか、problem+json にする)
- 推薦された科目の集計を SQL で取りたくなったとき
- 時間割の誤りの修正を、作った道標にも反映したくなったとき
