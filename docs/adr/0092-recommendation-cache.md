# 0092. 推薦の結果を職業名と条件の組で 7 日残し、同じ組の道標は LLM を呼ばずに作る

- ステータス: 承認
- 日付: 2026-11-05

## 文脈

- 道標を 1 件作るのに 10〜30 秒と約 1 円かかる(ADR 0029、0038)。そのほとんどは選び直し(3 回の多数決、ADR 0051)で、読み取りはプロセスの中で職業名ごとに覚えている(ADR 0052)が、選び直しは毎回呼んでいる
- 推薦(読み取りの結果と、選んだ授業と理由)は、職業名、学科、残りの学期、年度、推薦の候補から除く授業(もう取った授業、ADR 0035)が同じなら、利用者に依らない。利用者ごとに違うのは、そのあとの配置(クラスの選択、もう取った授業の扱い)だけ
- 同じ学生が同じ職業で作り直すとき、別の学生が同じ職業で作るとき、どちらも待ちと費用が無駄になる。動画や提出で見せるときも、10〜30 秒の待ちは目立つ
- 1 日の上限(ADR 0038)は費用の歯止めとして置いた。LLM を呼ばない道標をどう数えるかも決めが要る

## 検討した選択肢

置き場

1. DB の表に、鍵と推薦(JSONB)と期限を置く。worker と backend のどちらからも見え、再起動しても残る
2. worker のプロセスの中に、読み取りと同じ形で覚える。再起動で消え、worker を増やすと共有されない
3. 道標の表(`plans`)から同じ条件の最新の道標を探して流用する。利用者が消したり退会したりすると消え、指示文やモデルの指紋を持たず、持ち主の境界を跨いで読む
4. 残さない(今のまま)

残す期間

1. 1 日
2. 7 日
3. 30 日

当たった道標の上限の数え方

1. 今のまま数える(1 人 1 日 3 件、全体 30 件)
2. 費用がかからないので数えない

## 決定

高橋さんが、置き場は 1、期間は 7 日、上限は今のまま数えることを選んだ。

- 鍵は、職業名(API が前後の空白を除いた文字列そのまま)、学科、年度、残りの学期の並び、候補から実際に外れる授業コードの並び(検索と同じ決まり `left_out_codes` で、もう取った授業と同じシラバスのページの授業のうち、その学科で残りの学期に開講されるもの。外れない授業は候補を変えないので鍵を分けない)、推薦の作りの指紋の組(`RecommendationKey`)。指紋は、読み取りと選び直しのモデル、埋め込みのモデルと次元、検索の取り方(`SEARCH_BY_SKILL`)、候補の数、多数決の回数と残す票の下限と、推薦を作るモジュール(読み取り、検索、順位付け、抜粋、選び直し、多数決、LLM と埋め込みの呼び出し)のソースから作る。設定かコードを替えると鍵が変わり、前の推薦は当たらずに期限で消える
- 残すのは推薦(読み取りの結果、選んだ授業と理由、候補、外した礎)で、道標の結果と同じ JSON の形(版つき)。配置は残さず、毎回その利用者の条件で置き直す
- 期限は作った時刻から `RECOMMENDATION_CACHE_DAYS` 日(既定 7、0 で残さない)。当たっても期限は延ばさない。期限の切れた行は、worker が 1 日 1 回の片付け(消した道標の日時を消すのと同じ合図)で消す
- 当たった道標は、検索と選び直しの段を飛ばして配置に進む。記録(ADR 0087)には読み取りの段(残した推薦を探す時間)と配置の段だけが残り、LLM の使用は 0 で `report` の費用には入らない。当たりと外れはどちらもログに出す(「残した推薦を使います」「残した推薦が無いので作ります」)ので、当たる割合はログから数える
- 科目データを入れ替える `ingest timetable`、`ingest syllabi`、`embed` は、終わりに残した推薦を全て消す(推薦は科目データに依り、鍵は科目データを持たないため)。本番で科目の表を空にして戻すときも、同じ理由で `remembered_recommendations` を一緒に空にする(手順書に書く)
- 残した推薦を読めない、残せないときは、ログに残して推薦を作り直す(道標を失敗にしない)
- 当てるのは worker と `plan create` だけ。`recommend`、`evaluate_selection`、`experiment` は LLM を測る道具なので当てない(組み立てで分ける)
- 1 日の上限は今のまま数える。上限は費用だけでなく乱用の歯止めでもあり、数え方を分けると ADR 0038 の決まりが複雑になる

## 理由

- 推薦が利用者に依らないことは、推薦の入力(職業名、学科、残りの学期、年度、除く授業)が全て鍵に入ることで保てる。利用者ごとの違いは配置で吸収する
- DB に置けば、worker の再起動や複数の worker でも共有でき、期限と指紋で古い推薦を自然に捨てられる
- 7 日は、同じ学生が週のうちに作り直す範囲を覆い、指示文やモデルを替えたあとの古い推薦が長く残らない長さ
- 職業名を正規化しない(全角と半角、空白の違いは別の鍵)のは、残した推薦の読み取りの結果に職業名がそのまま入り、別の綴りの利用者の画面に出てしまうのを避けるため。同じ綴りだけを当てれば、画面に出る職業名はその人の入力のまま

## 受け入れたトレードオフ

- 同じ職業名でも綴りが違えば当たらない。当たる割合はログで分かるので、必要なら正規化を足す
- 作るたびの違い(選び直しの揺れ)が、7 日の間は同じ組で出なくなる。揺れを見せる道具は `experiment` に残る
- 表が 1 つ増え、推薦の JSON の形を道標の結果と共有するので、形を変えるときは両方を直す。表は鍵(ハッシュ)と推薦と時刻だけで、鍵の部品は持たない(推薦の JSON に職業名が入る)
- 当たった道標の記録(ADR 0087)は、LLM の使用が 0 で検索と選び直しの段が無いことで見分ける。印の列は持たない
- 推薦を作るモジュールを書き換えると(整形だけでも)指紋が変わり、残した推薦は当たらなくなる。指紋に入れるモジュールの一覧(`RECOMMENDING_MODULES`)に漏れがあると、その変更では当たり続ける

## 再検討する条件

- 推薦が利用者ごとに変わるようになったとき(除く授業以外の個人の条件を推薦に渡すとき)
- 当たる割合が低く、表を持つ意味が無いとき
- 指示文やモデルを頻繁に替えるようになり、7 日が長すぎるとき
