# 0098. 試験のカバレッジは、backend は行と分岐、frontend は表示の決まりを CI で測り、今の値より下がったら落とす

- ステータス: 承認
- 日付: 2026-11-07

## 文脈

- 試験は backend 919 件、Vitest 160 件、画面の通しの試験 236 件あるが、どこを試験しているかの数字が無かった
- 2026-11-07 に測ると、backend の行と分岐を合わせたカバレッジは 88.9%(行 89.7%、分岐 84.9%)だった。層ごとには、domain が行 99.7%、分岐 98.1%、application が 99.7% と 98.5%、infrastructure が 92.0% と 77.8%、presentation が 77.4% と 73.6%。presentation の低さは、手元で手で流す取り込みと取得の CLI(`ingest`、`fetch_syllabus`、`syllabus`、`timetable`)にほぼ試験が無いため
- frontend の Vitest は `src/lib` の表示の決まりを試験していて、文 99.5%、分岐 94.8% だった(Next のサーバーだけで動くモジュールと定数だけのファイルを除いた値。含めると文 96.5%)。部品と画面は Playwright の通しの試験で確かめていて、Vitest の数字には入らない
- 高橋さんの洗い出しで「カバレッジを測って載せる」を、お金を使わずにやると決めた

## 決定

- backend は pytest-cov で `app` の行と分岐を測り(`pyproject.toml` の `[tool.coverage]`)、CI の backend の job は `pytest --cov --cov-fail-under=88` で流して、行と分岐を合わせて 88% を下回れば落とす。下限は CI の命令にだけ置き、DB の結合試験が飛ぶ手元の `pytest --cov` は数字を出すだけにする(DB なしでは 86% ほどになる)。表は job の要約に書く
- frontend は `@vitest/coverage-v8` で `src/lib` の表示の決まりだけを測り(試験、生成した `schema.ts`、Next のサーバーだけで動く `fonts.ts`、`session.ts`、`sign-out.ts`、定数だけの `motion.ts`、`theme.ts` を除く)、文 97%、分岐 93%、関数 98%、行 97% を下回れば落とす。CI の frontend の job は `pnpm test --coverage` で流し、要約を job の要約に書く
- 下限は今の値の少し下に置く。試験を足して上がったら下限も上げる。下げるのは、試験しにくいコードを足す理由を ADR に書いたときだけ
- README の品質の節に、層ごとの数字を載せる。バッジは外の仕組み(Codecov など)が要るので付けない

## 理由

- 層ごとに見ると、業務の決まり(domain と application)はほぼ全て試験していて、外とつなぐ部分(infrastructure の分岐、手で流す CLI)が薄いことが数字で分かる
- 下限で落とせば、試験の無いコードが混ざっても気づける。今の値にそろえれば、すぐに CI が落ちることはない
- 外のサービスを使わず、アカウントも要らない

## 受け入れたトレードオフ

- 行と分岐のカバレッジは、試験の良さ(正しく確かめているか)を測らない。下限は「試験の無いコードを入れない」ための歯止めで、目標ではない
- 取り込みと取得の CLI は、実ページを置かない決まり(ADR 0043)で試験しにくく、低いまま受け入れる
- 部品と画面のカバレッジは測らない(通しの試験で確かめる)

## 再検討する条件

- 取り込みと取得の CLI を CI で流すようにしたとき
- 下限で関係の無い PR が落ちることが続いたとき
