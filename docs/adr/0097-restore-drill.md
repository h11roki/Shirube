# 0097. バックアップは毎週、使い捨てのコンテナに戻して、本番のスキーマと科目の表と合うかを確かめる

- ステータス: 承認
- 日付: 2026-11-07

## 文脈

- ADR 0075 で、DB 全体を毎日 `pg_dump` し、7 日分をサーバーに残すと決めた。戻す手順は書いたが、一度も戻したことがなく、戻せるかは分かっていなかった
- 2026-11-07 に、一番新しいバックアップ(11-06、11MB)を使い捨てのコンテナに戻してみた。7 秒で戻り、科目の表は本番と同じだった。一方で、バックアップのスキーマは 0011 で、本番は 0012 だった(バックアップのあとにマイグレーションを流していた)。手順書の戻し方はマイグレーションを流さず、そのまま起動していたので、古いスキーマで新しいコードが動くところだった
- 高橋さんの洗い出しで「バックアップから戻す練習をして記録する」を、お金を使わずにやると決めた

## 決定

- `restore-drill.sh` を足し、サーバーの cron で毎週日曜の 4:30(毎日のバックアップの 30 分後)に流す
  1. `~/deploy.lock` を取る(入れ替えの途中の本番と比べないよう。入れ替えが 30 分で終わらなければ演習しない)
  2. 23 時間より新しいバックアップのうち一番新しいもの(その日の 4 時のもの)を、本番の db のコンテナと同じイメージ(タグでなく ID)で、ネットワークから切り離し(`--network none`)、データをメモリの上にだけ置く(`--tmpfs` を 256MB、メモリを 512MB までに限り、本番を巻き込まない)使い捨てのコンテナに、本番の戻し方と同じ 1 つのトランザクションで戻す。23 時間より新しいバックアップが無ければ、毎日のバックアップが止まっているので落とす
  3. 本番の backend のコンテナと同じイメージで、そのコンテナにマイグレーションを流す
  4. スキーマの版が本番と同じか、利用者のデータの表(`users`、`plans`、`taken_courses`、`deleted_plans`、`plan_builds`、`remembered_recommendations`。バックアップのあとに変わる)を除く全ての表の行の数が本番と同じかを、両側で 1 回ずつの問い合わせで見る。今は科目の 5 つの表になる。除く一覧は手で持つので、表が足されれば既定で比べる側に入る
  5. かかった秒、戻す前と後のスキーマの版、利用者と道標の数を 1 行書き、コンテナを消す(名前の無いボリュームも残さない)。起動しない、戻せない、合わないときは、理由を書いて 1 で終わる
- 戻しの手順を演習と同じ形にする。毎日のバックアップと入れ替えの lock を取り、DB を作り直して空の DB に戻し、マイグレーションを流してから起動する(今の DB の上に `--clean` で戻すと、あとのマイグレーションで足した表や外部キーが残り、落ちうる)
- プライバシーポリシーの「バックアップは障害で失ったデータを戻すときだけに使う」に、週に 1 回、サーバーの中の外とつながらないメモリの上に戻して数を数え、すぐに消すことを書き足し、改定の日付を上げる
- `restore-drill.sh` は CI の scripts の job で shellcheck にかける

## 理由

- バックアップは、戻せることを確かめて初めて役に立つ。戻す時間(今は 7 秒)も分かる
- 使い捨てのコンテナのメモリの上に戻すので、本番の DB には読むだけで、データはサーバーの外にも、ディスクの別の場所にも残らない
- 本番の backend のイメージでマイグレーションを流すので、古いバックアップから今のコードまで上げられるかも毎週確かめられる

## 受け入れたトレードオフ

- 演習の結果は `~/backups/drill.log` にだけ書き、外の監視(ADR 0095)には出さない。落ちたことに気づくには記録を見る
- 一時的に 2 つ目の Postgres が動く(小さいサーバーで数十 MB、数秒)
- バックアップはサーバーの中にしか無いので、ディスクごと失ったときの戻しは確かめていない(ADR 0075 の受け入れたトレードオフのまま)

## 再検討する条件

- バックアップをサーバーの外に置くとき(外から取ってきて戻す演習にする)
- 戻す時間が分単位になるほどデータが増えたとき
