# 0097. バックアップは毎週、使い捨てのコンテナに戻して、本番のスキーマと科目の表と合うかを確かめる

- ステータス: 承認
- 日付: 2026-11-07

## 文脈

- ADR 0075 で、DB 全体を毎日 `pg_dump` し、7 日分をサーバーに残すと決めた。戻す手順は書いたが、一度も戻したことがなく、戻せるかは分かっていなかった
- 2026-11-07 に、一番新しいバックアップ(11-06、11MB)を使い捨てのコンテナに戻してみた。7 秒で戻り、科目の表は本番と同じだった。一方で、バックアップのスキーマは 0011 で、本番は 0012 だった(バックアップのあとにマイグレーションを流していた)。手順書の戻し方はマイグレーションを流さず、そのまま起動していたので、古いスキーマで新しいコードが動くところだった
- 高橋さんの洗い出しで「バックアップから戻す練習をして記録する」を、お金を使わずにやると決めた

## 決定

- `restore-drill.sh` を足し、サーバーの cron で毎週日曜の 4:30(毎日のバックアップの 30 分後)に流す
  1. 一番新しいバックアップを、ネットワークから切り離した(`--network none`)使い捨ての `pgvector/pgvector:pg16` のコンテナに戻す
  2. 本番の backend のイメージで、そのコンテナにマイグレーションを流す
  3. スキーマの版が本番と同じか、科目の 5 つの表(`course_sections`、`syllabi`、`syllabus_codes`、`syllabus_chunks`、`embeddings`)の行の数が本番と同じかを見る。利用者と道標の表はバックアップのあとに変わるので、行の数を書くだけにする
  4. かかった秒、戻す前と後のスキーマの版、利用者と道標の数を 1 行書き、コンテナを消す。合わなければ理由を書いて 1 で終わる
- 戻しの手順に、戻したあとのマイグレーションを足す
- `restore-drill.sh` は CI の scripts の job で shellcheck にかける

## 理由

- バックアップは、戻せることを確かめて初めて役に立つ。戻す時間(今は 7 秒)も分かる
- 使い捨てのコンテナで戻すので、本番の DB には読むだけで、データはサーバーの外に出ない(プライバシーポリシーの範囲のまま)
- 本番の backend のイメージでマイグレーションを流すので、古いバックアップから今のコードまで上げられるかも毎週確かめられる

## 受け入れたトレードオフ

- 演習の結果は `~/backups/drill.log` にだけ書き、外の監視(ADR 0095)には出さない。落ちたことに気づくには記録を見る
- 一時的に 2 つ目の Postgres が動く(小さいサーバーで数十 MB、数秒)
- バックアップはサーバーの中にしか無いので、ディスクごと失ったときの戻しは確かめていない(ADR 0075 の受け入れたトレードオフのまま)

## 再検討する条件

- バックアップをサーバーの外に置くとき(外から取ってきて戻す演習にする)
- 戻す時間が分単位になるほどデータが増えたとき
