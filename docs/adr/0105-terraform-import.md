# 0105. 本番の AWS の資源を Terraform に取り込み、今の形のまま plan の差が無いことを確かめる

- ステータス: 承認
- 日付: 2026-11-15

## 文脈

- 本番の AWS の資源(EC2 の t4g.small、セキュリティグループ、Elastic IP、SSH の鍵の組)は、2026-10-30 にコンソールの起動の手順で手で作った(ADR 0075、0076)。どの設定で作ったかはコンソールにしか残っておらず、作り直すときや設定を確かめるときに、コンソールを開いて 1 つずつ見るしかない
- 高橋さんは 2026-11-06 に、IaC は Terraform にし、今の資源を import して plan の差が無いことを確かめ、state は手元に置くと決めた(ポートフォリオの作業の一覧)
- アカウントは新しい登録(Sign up for AWS (new))の無料プランで、ルートユーザーが無い(ADR 0076)。手元の CLI と SDK の鍵は、AWS Settings の「AI コーディングツールで AWS の認証情報を使う」で作ったプロファイルを `aws login` で取る。12 時間使え、90 日まではブラウザで許可し直さずに延ばせる。IAM のユーザーとロールは無料プランでも作れるが、高度な機能(IAM Identity Center など)は有料プランに上げないと使えず、上げると戻せない
- 取り込むときに読んだ今の資源には、直したい所がある
  - セキュリティグループ(`launch-wizard-1`)が SSH(22 番)をどこからでも受ける。入るには鍵が要る。`docs/development.md` の手順と ADR 0094 には「22 を自分の IP だけに開ける」と書いてあり、文書と本番が食い違っていた
  - ルートのボリューム(gp3、20GB)が暗号化されていない。暗号化するにはボリュームを作り直す
  - CPU のクレジットが unlimited で、使い続けるとクレジットの外の分が無料プランのクレジットから引かれる

## 検討した選択肢

取り込む範囲

1. EC2、セキュリティグループ、Elastic IP、SSH の鍵の組の 4 つ(VPC とサブネットは既定のものを ID で指す)
2. 1 に既定の VPC、サブネット、インターネットゲートウェイも足す
3. EC2 だけ

取り込みの仕方

1. `import` のブロックを設定に残し、取り込んだ設定を手で整えて、plan の差が無くなるまで合わせる
2. `terraform import` のコマンドで state にだけ入れる

state の置き場

1. 手元だけ(git の管理外)
2. S3 とロックの表

SSH の口

1. この変更では今のまま取り込み、次の変更で SSM Session Manager に移して 22 番を閉じる
2. この変更で自宅の IP だけにする
3. 開けたままにし、理由を書く

CI での確かめ

1. `terraform fmt -check` と `terraform validate`
2. 1 に tflint を足す
3. CI では確かめない

## 決定

高橋さんが、取り込みは今の形のまま、SSH は次の変更で閉じる、CI は fmt と validate、を選んだ(2026-11-15)。

- `infra/` に Terraform の設定を置き、EC2、セキュリティグループ、Elastic IP、SSH の鍵の組の 4 つを取り込む。既定の VPC とサブネットは ID で指すだけにする。地域は `ap-southeast-2` に決める
- 取り込みは `import` のブロックで書き、設定に残す。state は手元だけに置くので、state を無くしたときや別の機械で始めるときも、同じ設定から取り込み直せる。取り込みは AWS の資源を何も変えない
- 合わせたかどうかは、`terraform plan` が「取り込み 4、追加 0、変更 0、削除 0」になることで確かめる。取り込んだあとは「No changes」になる
- state(`*.tfstate`)と `.terraform/` は git の管理外にする。state には資源の ID と IP しか入らないが、手元だけに置く約束どおりにする。プロバイダの版を固定する `.terraform.lock.hcl` はコミットする
- 鍵はプロバイダに書かず、`AWS_PROFILE` で渡す(手元のプロファイルの名前を設定に持ち込まない)
- CI の scripts の job で `terraform fmt -check` と、バックエンドを使わない `terraform init` のあとの `terraform validate` を流す。CI には AWS の鍵を渡さない
- AWS のプロバイダの版は Dependabot が、ほかの依存と同じに毎週、出てから 7 日経った版だけを上げる(ADR 0096)。CI では差を確かめられないので、その PR は手元で plan が No changes のままかを確かめてからマージする
- 取り込んだ 4 つ全てに `prevent_destroy` を付け、作り直しや削除になる plan を止める。EC2 のルートのボリュームに DB とバックアップがあり、Elastic IP が変わると DuckDNS の向き先も変わり、鍵の組を作り直すと手元の秘密鍵で入れなくなり、セキュリティグループは EC2 に付いたままでは消せず apply が途中で止まるため。`infra/shirube.pub` は、手元の秘密鍵から作った公開鍵と同じであることを確かめた
- Terraform の本体の版は CI と同じ 1.17 の系列に絞る(`~> 1.17.0`)。CI の `init` は `-lockfile=readonly` で、コミットしたロックと違う版を選べば落ちる
- state を無くして取り込み直すときも、保存した plan が取り込みだけであることを確かめてから apply する
- SSH の鍵の組は、AWS が取り込むときに公開鍵を返さないので、公開鍵(`infra/shirube.pub`、秘密ではない)を設定に置き、差としては見ない(`ignore_changes`)。見ないと、取り込むたびに鍵の組を作り直す差が出る
- 今の SSH の口、暗号化していないボリューム、unlimited のクレジットは、取り込むときにはそのままにする。SSH は次の変更で SSM Session Manager に移して 22 番を閉じ、ADR に書いてから apply する。ボリュームの暗号化とクレジットは、作り直しや費用の決めごとと一緒に、そのとき決める

## 理由

- 4 つは、この本番を作るときにコンソールで選んだものの全てで、サーバーを作り直すのに要るのはこれだけ。既定の VPC などは AWS が作ったもので、取り込んでも書くことが無い
- 今の形のまま取り込めば、本番を一切変えずに、コンソールにしか無かった設定をコードで読めるようになる。直したい所を同じ変更で直すと、取り込みの誤りと設定の変更の区別がつかなくなる
- 利用者は 1 人で、state を同時に触る人がいない。S3 とロックの表は少額でも費用と管理が増え、今の「お金のかかることはしない」と合わない。state を無くしても `import` のブロックから作り直せる
- CI に AWS の鍵を渡すと、鍵の扱いが増える(ADR 0094 で CI に SSH の鍵も持たせないと決めた)。書き方と構文は鍵なしで確かめられる

## 受け入れたトレードオフ

- 資源の ID を設定に直に書いている。サーバーを作り直すと ID が変わるので、そのときは設定と `import` のブロックを直す
- plan の差は手元でしか確かめないので、コンソールで手で変えても CI は気づかない。設定を変えるときと、月に 1 度ほど手元で plan を流して確かめる
- セキュリティグループの名前と説明は起動の手順が付けたまま(`launch-wizard-1`)。名前を変えるとグループを作り直すことになるので、取り込むときは変えない

## 再検討する条件

- サーバーを 2 台以上にするか、RDS や ALB を足すとき(ADR 0102 の段階 5)。state を S3 に移し、ロックを足す
- 無料プランを有料プランに上げるとき(ADR 0076)。鍵の取り方と、IAM で Terraform 用の権限を絞ることを見直す
- 手で設定を変える人が増えたとき。CI で plan を流すことを考える
